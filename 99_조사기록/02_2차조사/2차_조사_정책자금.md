# 2차 조사 — 소상공인 정책자금 탐색과 신청

- 조사 기준일: 2026-08-13
- 조사 범위: 국내 사용자 반응, 기존 서비스, 공개 데이터, 인증·신청 연결 가능성, 해외 벤치마크
- 주의: 사용자 게시물은 당사자의 자가진술이다. 사실관계가 독립적으로 확인된 민원 통계로 간주하지 않고, 반복되는 문제 가설을 찾는 근거로 사용했다.

## 1. 먼저 드러난 결론

문제는 단순히 “정책자금 공고를 못 찾는다”에 머물지 않는다. 현재도 소상공인정책자금 사이트, 소상공인365, 기업마당, 민간 매칭 서비스가 공고와 안내를 제공한다. 사용자 사례에서 더 반복된 마찰은 다음 네 가지다.

1. 내 상황에 맞는 자금 종류와 담당 기관을 구분하지 못한다.
2. 자격조건과 제출서류를 해석하고 준비하는 데 부담을 느낀다.
3. 공단 확인서 이후에도 보증기관과 은행 심사가 남는 다기관 절차를 한 번에 이해하지 못한다.
4. 예산 소진·접속 경쟁·로그인·인증 때문에 “자격이 있어도 신청 자체를 못 했다”고 느낀다.

공개 API를 이용하면 **공고 발견, 조건 정리, 제출서류 준비, 신청 URL 연결**까지는 파트너십 없이 구현할 수 있다. 그러나 대출 신청 제출, 신용·기존부채 확인, 보증 및 은행 심사, 최종 실행은 본인·사업자 인증과 기관 권한이 필요하다. 현실적인 무제휴 MVP의 상한은 **실행 단계 3(신청 준비) + 일부 단계 2(정확한 신청 링크)**다.

### 사용자 반응에서 읽히는 핵심

- “공고를 못 찾음”과 “찾았지만 내가 되는지 모름”은 다른 문제다.
- 공단의 지원대상 확인과 금융기관의 최종 대출 승인은 다른 사건이다.
- 전화상담, 센터 방문, 카페 후기, 유튜브, 컨설턴트는 현재의 비공식 인터페이스다.
- 한 번 배우면 끝나는 지식 문제가 아니다. 자금 종류, 사업 상태, 접수기간, 예산, 서류가 계속 달라진다.

### 기존 서비스가 있는데도 남는 이유

1. 서비스가 기관별 목적에 맞춰져 있고 사용자의 전체 여정은 소유하지 않는다.
2. 공고 데이터와 심사 데이터가 분리되어 있다.
3. “지원대상일 가능성”과 “최종 승인” 사이의 불확실성을 설명하지 않으면 매칭 결과를 믿기 어렵다.
4. 공개 정보는 많지만 서류 준비와 기관 이동을 개인의 현재 상태에 맞춰 이어주는 작업공간이 약하다.

## 4. 세 Mock 프로필로 본 데이터 충족도

실제 개인정보나 허위 사업자정보를 입력하지 않고 공개된 조건만으로 재구성했다. 아래는 승인 예측이 아니라 **어떤 데이터를 공개 API로 처리할 수 있고 무엇이 남는지**를 보는 테스트다.

| Mock 프로필 | 공개 정보로 좁힐 수 있는 항목 | 추가로 필요한 정보 | 제품이 줄일 수 있는 일 | 끝까지 못 하는 일 |
|---|---|---|---|---|
| 개업 6개월 음식점 | 업력, 업종, 지역, 모집기간, 지원목적, 신청기관 | 매출·상시근로자, 임대차, 세금 체납, 제외업종 세부, 대표자 신용·기존대출 | 해당 가능성이 높은 자금군, 제외 사유 질문, 단계별 서류 체크리스트, 정확한 신청 URL | 공식 적격 확정, 신용조회, 보증·은행 승인 |
| 업력 3년 온라인 판매업·매출 감소 | 업종, 업력, 지역, 매출감소 요건이 공고에 명시된 경우 조건 비교 | 감소를 증명할 기간별 매출, 통신판매·사업자 상태, 기존 지원 이력, 체납 | 어떤 매출자료를 어느 기간으로 뽑아야 하는지 안내, 공고별 차이 비교 | 자료의 진위 확인과 기관 제출 |
| 소규모 서비스업·신용/기존부채 불명확 | 공고의 일반 지원대상과 제외업종 | 대표자 신용점수, 연체, 기존 보증·대출 잔액, 부채상환능력 | 공개조건 통과 여부와 “금융심사에서 다시 확인할 항목”을 분리해 설명 | 승인확률의 신뢰도 높은 산출, 최종 실행 |

## 5. 공개 API와 실행 연결 가능성

### 중기부 지원사업 공고 API

[공공데이터포털 상세](https://www.data.go.kr/data/15157820/openapi.do)에서 확인한 조건은 다음과 같다.

- REST, JSON/XML, 전국 범위, 무료
- 개발계정 자동승인, 운영계정 심의승인
- 개발 트래픽 10,000회, 운영은 활용사례 등록 후 증량 신청 가능
- 공고 제목·개요·지역·대상·기간·신청방법·첨부파일·문의처·신청 URL 제공
- 라이선스는 공공누리 제3유형이므로 출처표시와 변경금지 조건을 구체적으로 검토해야 한다.

이 API로 가능한 것은 공고 수집, 필터링, 설명, 원문·신청 URL 연결이다. 개인의 신용정보나 접수 결과는 포함되지 않는다.

### 실행 단계 판정

| 단계 | 의미 | 현재 가능성 | 근거와 조건 |
|---|---|---|---|
| 1 | 정보만 제공 | 즉시 가능 | 공고 API와 공식 원문 사용 |
| 2 | 정확한 외부 신청 링크 | 조건부 즉시 가능 | API에 신청 URL이 있으면 가능. 소상공인정책자금의 일부 버튼은 고정 링크가 아니라 세션·자바스크립트 동작이라 상품별 연결 안정성 확인 필요 |
| 3 | 입력·서류 준비 | 즉시 가능 | 공고 조건을 질문으로 변환하고 서류 상태를 관리할 수 있음. 신분증·인증서 원본을 MVP가 보관하지 않는 설계가 안전 |
| 4 | 외부 화면과 나란히 안내 | 보류 | 사용자가 PiP를 보류했으며, iframe 허용 여부도 공식 근거를 찾지 못함 |
| 5 | 공식 화면 임베드·부분 실행 | 미확인/파트너십 필요 | 공개 신청 API·공식 임베드 문서를 찾지 못함 |
| 6 | 우리 서비스에서 제출·결과 수신 | 현재 무제휴로 불가능 | 사업자 본인인증, 서명, 공단·보증기관·은행의 업무 권한과 결과 연계 필요 |

### 인증·개인정보 경계

- 공식 신청은 통합회원 또는 사업자 계정과 본인인증을 요구한다.
- 매칭용 최소 프로필은 업종·지역·업력·매출구간처럼 비민감 범주부터 시작할 수 있다.
- 신용·연체·대출잔액을 실제로 가져오려면 공개 공고 API가 아니라 금융정보 권한이 필요하다.
- MVP에서는 “조건상 후보”, “추가 확인 필요”, “공식 심사 대상”을 명시적으로 구분해야 한다.

## 6. 해외 벤치마크

### 영국 British Business Bank Finance Finder

[Finance Finder](https://www.british-business-bank.co.uk/start-your-journey/finance-finder)는 몇 가지 질문으로 금융 유형을 탐색하는 1단계와, 금융 신청을 준비하는 2단계를 분리한다. 추천이 곧 승인이라는 인상을 주지 않고 독립적인 전문 조언을 권한다.

국내에 가져올 점은 “AI 매칭”이라는 이름보다 다음 구조다.

- 탐색과 준비를 별도 단계로 보여준다.
- 각 결과가 왜 후보인지 설명한다.
- 다음 기관에서 다시 확인할 내용을 남긴다.

### GOV.UK Finance and Support

[GOV.UK 검색](https://www.gov.uk/business-finance-support)은 지원 유형, 사업 단계, 업종, 직원 수, 지역으로 현재 100개 이상의 제도를 필터링한다. 상세 페이지가 각 제공기관의 신청 경로로 연결되는 구조다. 국내 기업마당과 유사하며, 검색만으로 전체 문제를 해결하지 못한다는 비교 근거다.

## 7. 팀이 실질적으로 줄일 수 있는 부분

### 강하게 남아 있는 문제

- 자금 이름과 기관이 아니라 “내 사업의 현재 상황”에서 출발하는 탐색
- 공단 확인, 보증, 은행 심사의 차이를 한 화면에서 설명
- 공고별 제출서류를 중복 제거한 준비 목록
- 예산·마감·공고 변경과 사용자의 진행 상태를 함께 관리
- 컨설턴트가 대신하던 쉬운 설명과 순서 정리를 무료·출처 기반으로 제공

### 이미 해결에 가까운 부분

- 광범위한 공고 수집과 단순 필터링
- 일반적인 정책자금 설명
- 공식 신청 사이트로 보내는 포털

### 파트너십 경계

- 공단·보증기관·은행 신청서를 우리 화면에서 제출
- 본인 신용·부채·연체정보 자동 조회
- 접수·심사·승인 상태 콜백
- 공식 상담 예약이나 은행 실행을 우리 서비스에서 완료

### AI를 억지로 붙이지 않아도 되는 부분

- 업종·지역·업력·기간 같은 구조화 조건은 규칙 기반 필터가 더 투명하다.
- AI가 유용할 가능성이 있는 곳은 긴 공고의 조건·예외 추출, 사용자 질문을 공고 근거에 연결한 설명, 서류명 표준화다.
- AI가 승인 여부를 단정해서는 안 되며 원문 문장과 추가 확인 항목을 함께 보여줘야 한다.

## 8. 아직 모르는 것과 기관 확인 질문

공개 화면만으로 확인되지 않아 향후 담당기관에 물어볼 질문이다.

1. 중기부 공고 API의 `신청 URL`은 상품·공고별로 얼마나 안정적으로 유지되는가?
2. 공고의 수정·마감·예산 소진 상태를 실시간 또는 증분 방식으로 받을 수 있는가?
3. 소상공인정책자금의 길잡이·신청 화면에 제3자 딥링크가 허용되는가?
4. 공식 신청서 초안 데이터를 사전에 만들고 사용자가 공식 화면에서 불러오는 연계 규격이 있는가?
5. 접수 결과 또는 보완요청을 제3자 서비스가 사용자 동의 아래 받을 수 있는 API가 있는가?
6. 공단·지역신보·은행 사이에서 중복 제출되는 서류 중 대체 가능한 것은 무엇인가?
7. 공공데이터의 공공누리 제3유형 ‘변경금지’가 조건 정규화·요약·AI 설명에 어떻게 적용되는가?

## 9. 현재 판단

이 후보는 “정책자금을 찾아주는 또 하나의 검색기”로 만들면 기존 서비스와 강하게 겹친다. 반면 **공고 근거가 붙은 후보 설명 → 기관별 심사 차이 표시 → 중복 없는 서류 준비 → 정확한 신청 링크 → 진행상태 체크**로 범위를 잡으면 현재 사용자 우회법을 상당 부분 대체할 수 있다.

다만 최종 대출 실행을 우리 웹서비스 안에서 끝내는 것은 공개 API만으로 불가능하다. MVP는 그 한계를 숨기지 않고, 사용자가 외부 신청에 들어가기 전에 잘못된 후보·서류 누락·기관 혼동을 얼마나 줄였는지 보여주는 방향이 현실적이다.
