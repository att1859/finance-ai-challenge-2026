# 2차 조사 — 커뮤니티에서 새로 찾은 금융 문제 후보

- 조사 기준일: 2026-08-15
- 조사 대상: 기존 세 후보의 변형이 아닌 신규 금융 문제
- 남긴 후보: 멀티채널 판매자 정산 차이 감사 / 카드 혜택 누락 감사·문의 준비
- 문제 발견 원칙: 공문과 뉴스가 아니라 국내 커뮤니티 질문, 지식인, 앱 리뷰에서 반복되는 사용자 경험을 출발점으로 삼았다.
- 공식 문서의 용도: 문제의 존재를 주장하는 근거가 아니라, 기존 서비스 범위와 API·인증·실행 가능성을 검증하는 데만 사용했다.
- 결론 유보: 이 문서는 두 후보의 실재성과 구현 경계를 확인한 자료다. 점수나 최종 순위는 정하지 않는다.

## 1. 넓게 찾은 뒤 두 후보를 남긴 방식

다음 조건을 모두 만족하는 문제를 찾았다.

1. 사용자가 한 번 사실을 배우면 끝나는 문제가 아니라 거래가 생길 때마다 반복된다.
2. 정책 변경만으로 해결되는 문제가 아니라 사용자의 실제 업무 흐름을 줄일 수 있다.
3. 기존의 정책자금·정기결제·맞춤형 지원과 사용자, 데이터, 실행 흐름이 다르다.
4. 여러 사용자가 비슷한 혼란이나 수작업을 말한다.
5. 최종 실행권한을 확보하지 못해도 조회·대사·준비·정확한 연결 중 일부를 MVP로 만들 수 있다.
6. 공개·무료 자료나 사용자가 직접 제공한 파일로 세 개의 Mock 프로필을 시연할 수 있다.

처음에는 이사 때 공과금·자동이체·주소변경을 한 번에 정리하는 문제도 살펴봤다. 사용자 불편은 있었지만 금융 문제의 중심성이 약하고 기존 일괄 주소변경·체크리스트와의 차별점이 덜 분명해 이번 두 후보에는 넣지 않았다.

## 2. 후보 A — 멀티채널 판매자의 주문·정산·실입금 차이 감사

### 2.1 한 문장 정의

스마트스토어·쿠팡·ESM·자사몰 등 여러 판매채널의 **주문금액, 수수료·쿠폰·반품, 정산예정액, 실제 은행 입금액을 주문 단위로 맞추고 차이의 이유와 미정산 의심 건을 설명하는 도구**다.

단순히 “다음 정산일에 얼마가 들어온다”를 보여주는 정산 달력이 아니다. 사용자가 궁금한 것은 다음 세 가지다.

- 총매출과 입금액이 왜 다른가?
- 정상적인 시차·수수료·반품 차이인가, 확인해야 할 누락인가?
- 플랫폼에 문의하려면 어느 주문과 어느 정산내역을 근거로 제시해야 하는가?

### 2.3 사용자가 현재 하는 비공식 우회법

아래는 공식 지원 기능이 아니라 사용자가 직접 대신하는 방식이다.

- 각 판매자센터에서 주문·정산 CSV를 내려받아 엑셀의 조회 함수로 맞춘다.
- 은행 입금내역을 별도로 내려받아 날짜와 금액으로 눈대중 대조한다.
- 부가세 신고 때 홈택스·플랫폼 자료를 보며 차이가 나는 항목을 카페나 지식인에 묻는다.
- 미정산이 의심되면 주문번호·캡처·입금일을 직접 모아 플랫폼 고객센터에 문의한다.
- [크몽의 주문·정산 CSV 마진표 자동화](https://kmong.com/gig/765724)처럼 유료 엑셀·구글시트 제작을 의뢰한다.

이 우회법은 계산식을 한 번 배우면 끝나지 않는다. 주문, 취소, 반품, 쿠폰, 광고비, 정산주기가 계속 바뀌므로 새 파일이 생길 때마다 반복된다.

### 2.4 단계별로 분해한 사용자 여정

| 단계 | 현재 행동 | 만들 수 있는 가치 |
|---|---|---|
| 1. 자료 발견 | 각 플랫폼의 주문·정산·세금 메뉴를 찾음 | 채널별로 필요한 파일과 기간을 체크리스트로 안내 |
| 2. 자료 수집 | CSV 여러 개와 은행 입금내역을 내려받음 | 업로드 상태와 누락 기간을 표시 |
| 3. 항목 표준화 | 플랫폼마다 다른 주문번호·수수료·쿠폰 열을 엑셀로 정리 | 공통 주문·공제·정산 스키마로 변환 |
| 4. 대사 | 주문합계, 정산액, 입금을 날짜·금액으로 맞춤 | 주문→정산→입금 연결과 일대다·다대일 정산 처리 |
| 5. 차이 판단 | 늦게 들어올 돈인지, 수수료인지, 누락인지 추정 | 정상 시차·취소·반품·쿠폰·수수료·설명불가로 분류 |

### 2.6 왜 기존 서비스만으로 끝나지 않는가

현재 확인된 이유는 다음과 같이 층을 나눠 보아야 한다.

- **확인된 구조적 이유:** 각 플랫폼이 자기 플랫폼의 자료만 가진다. 은행 입금과 타 플랫폼 주문까지 연결하려면 별도 통합이 필요하다.
- **사용자 사례로 확인된 이유:** 사용자는 여전히 주문별 확인용 엑셀을 만들고, 매출·입금 차이를 커뮤니티에 묻는다.
- **가격 장벽 가능성:** 전문 정산·ERP 서비스는 월 과금이 있어 판매량이 적은 초보 판매자에게 부담일 수 있다. 실제 이탈률은 모른다.
- **정확성 미확인:** 기존 서비스가 분할정산·반품·플랫폼 쿠폰·판매자 쿠폰·광고비·부가세를 어느 수준까지 주문과 입금에 연결하는지는 직접 사용 전에는 알 수 없다.
- **아직 만들어지지 않은 것으로 보이는 부분:** 설명불가 차이를 주문 근거와 함께 문의 패키지로 만드는 흐름은 공개 제품 설명에서 찾지 못했다.

### 2.7 데이터·API·인증·외부 실행 가능성

#### 바로 확인된 공개 연결 수단

- [네이버 커머스API 건별 정산내역](https://apicenter.commerce.naver.com/docs/commerce-api/2.83.0/find-settle-by-case-pay-settle)은 건별 정산 조회를 제공한다. 일별 정산, 수수료 상세, 부가세 관련 API도 문서에 노출돼 있다.
- [쿠팡 Open API 매출내역 조회](https://developers.coupangcorp.com/hc/ko/articles/360033922413-%EB%A7%A4%EC%B6%9C%EB%82%B4%EC%97%AD-%EC%A1%B0%ED%9A%8C)는 주문번호, 매출·환불 구분, 매출인식일, 정산일, 배송비, 쿠폰, 서비스수수료와 부가세, 정산금액 등의 필드를 제공한다.
- [쿠팡 판매자 API 키 발급 안내](https://developers.coupangcorp.com/hc/ko/articles/20288952179993)에 따르면 판매자가 Wing에서 Open API 키를 발급하는 구조다.

#### 인증이 얼마나 필요한가

- 네이버: 판매자 앱 등록과 인증 토큰 처리가 필요하다. 아무 판매자의 자료를 공개적으로 가져오는 API가 아니다.
- 쿠팡: 해당 판매자가 자신의 API 키를 발급해 연결해야 한다. 비밀번호를 받는 방식이 아니라 공식 키를 사용해야 한다.
- 은행: 자동으로 계좌 거래를 가져오려면 금융기관 제휴나 마이데이터 등 별도 권한 검토가 필요하다.
- MVP: 은행 API를 붙이지 않고 사용자가 직접 받은 거래 CSV를 업로드하면 제휴 없이 대사 경험을 검증할 수 있다.

#### 우리 웹사이트 안에서 가능한 실행 단계

1. 정보만 제공: 가능
2. 플랫폼별 정확한 다운로드·API 발급 경로 연결: 가능
3. CSV/API 자료의 표준화와 대사 준비: 가능
4. 우리 웹에서 차이 분석·근거 확인: 가능
5. 공식 API를 통한 판매자 자신의 정산자료 자동 수집: 판매자 인증·앱 등록 조건부 가능
6. 플랫폼 정산을 수정하거나 지급을 실행하고 결과를 받기: 공개 API 근거 없음

문의 버튼을 우리 화면에 두더라도 플랫폼의 문의 접수 API가 없다면 `증빙 다운로드/복사 → 정확한 고객센터 화면 열기`까지만 약속해야 한다.

### 2.8 세 개의 Mock 프로필

| 프로필 | 상황 | 데모에서 보여줄 핵심 |
|---|---|---|
| 초보 판매자 | 스마트스토어와 쿠팡을 시작했고 900만 원 매출 중 통장에는 410만 원만 보임 | 정산예정일 때문에 아직 미입금인 정상 시차와 실제 미확인 금액을 분리 |
| 반품이 많은 판매자 | 쿠폰·배송비·부분반품·광고비가 섞여 총매출과 정산액이 크게 다름 | 한 주문의 공제 항목을 풀어 설명하고 실제 입금 묶음과 연결 |
| 신고 준비 판매자 | 네이버·ESM·쿠팡의 월 자료와 은행·세무자료 숫자가 맞지 않음 | 기간·매출인식 기준 차이를 보여주고 설명불가 주문 목록을 내보냄 |

### 2.9 MVP 범위

- 네이버·쿠팡 형식의 합성 CSV와 은행 거래 합성 CSV를 업로드
- 열 이름이 달라도 주문번호·거래일·정산일·정산액·입금액을 공통 구조로 변환
- `일치 / 정산대기 / 반품·취소 / 수수료·쿠폰 / 입금 묶음 / 설명불가`로 분류
- 설명불가 항목을 주문번호, 계산식, 예상 정산일, 관련 행과 함께 내보냄
- 실제 API 연결은 한 플랫폼만 선택 구현하거나, 데모에서는 연결 화면과 Mock 응답으로 범위를 명확히 표시
- 원본 파일은 분석 후 삭제하고 계좌·구매자 식별정보를 마스킹

### 2.10 AI가 꼭 필요한가

핵심 대사와 금액 계산은 규칙 기반이어야 한다. AI를 쓸 만한 곳은 다음뿐이다.

- 플랫폼마다 다른 CSV 열 이름을 공통 스키마 후보로 매핑
- 설명불가 사유를 사용자가 이해하는 문장으로 변환
- 고객센터 문의 초안을 생성

금액의 일치 여부와 수수료 계산 자체를 생성형 AI가 결정하게 하면 감사 도구의 신뢰가 떨어진다.

### 2.11 해외 벤치마크

[A2X](https://www.a2xaccounting.com/)는 Amazon·Shopify·eBay·Etsy·Walmart 등 여러 채널의 매출·수수료·세금을 정리하고, 지급액을 회계시스템의 예금과 맞추는 구조를 제공한다. 주문에서 현금까지의 감사추적을 별도 제품 범위로 둔 점이 국내 후보에 참고가 된다.

가져올 것은 해외 판매채널이 아니라 다음 설계다.

- 매출 대시보드와 지급 대사를 다른 문제로 분리
- 모든 차이에 원래 주문과 계산 근거를 남김
- 자동매칭과 사람이 확인해야 할 예외를 분리

### 2.12 추가 확인이 필요한 질문

2. 판매자는 월 과금 대신 어떤 가격과 데이터 입력 방식까지 수용하는가?

4. 한 입금에 여러 주문이 합쳐지거나 한 주문이 여러 번 정산될 때 플랫폼별 식별자가 안정적인가?
5. 사용자가 가장 원하는 결과가 현금흐름 예측인지, 누락 탐지인지, 세무자료 정리인지 인터뷰로 구분할 필요가 있다.

## 3. 후보 B — 카드 혜택 누락 감사와 문의 준비

### 3.1 한 문장 정의

사용자가 보유한 카드의 상품설명서와 월 거래내역을 비교해 **받았어야 할 할인·적립과 실제로 받은 혜택의 차이, 전월실적 제외 이유, 한도·시점 문제를 거래별로 설명하고 카드사 문의 근거를 만들어주는 도구**다.

`이번 달 전월실적이 얼마 남았는지`만 계산하는 앱이나 `어느 카드를 쓰면 좋은지` 추천하는 앱이 아니다. 핵심 질문은 다음과 같다.

- 나는 실적을 채웠다고 생각했는데 왜 혜택이 없나?
- 할인받은 결제의 전액이 실적에서 빠진 것인가, 할인액만 빠진 것인가?
- 잘못 적용된 것인지, 월 한도·업종분류·취소 반영 시점 때문인지 어떻게 확인하나?
- 카드사에 어느 거래와 약관 문장을 제시해야 하나?

### 3.3 사용자가 현재 하는 비공식 우회법

- 카드사 앱을 카드별로 열어 실적·혜택 메뉴를 각각 확인한다.
- 엑셀이나 메모장에 제외항목과 남은 실적을 직접 기록한다.
- 토스·뱅크샐러드의 예상치를 보고도 카드사 앱과 다시 대조한다.
- 실적이 애매하면 안전하게 몇 만 원을 더 결제한다.
- 혜택이 빠져도 이유를 찾지 못하면 커뮤니티에 거래 유형을 적어 질문한다.
- 카드사 고객센터 운영시간에 맞춰 전화하거나 상담 채널에 거래별로 다시 설명한다.

### 3.6 왜 기존 서비스만으로 끝나지 않는가

- **확인된 구조적 이유:** 카드사 앱은 자기 카드만 다루고, 통합 앱은 여러 카드의 서로 다른 약관을 자체 규칙으로 다시 구현해야 한다.
- **사용자 사례로 확인된 이유:** 통합 서비스가 있어도 사용자는 제외항목과 혜택을 카드사 앱에서 재확인하며, 틀린 내역을 고객센터에 수정 요청한다.
- **서비스 공백:** 더쎈카드 종료 뒤 동일한 수준의 대체재를 찾는 글이 여러 커뮤니티에 생겼다.
- **사용성 좋은 경우:** 체리피커처럼 사용자 규칙과 문자 기반 계산이 잘 맞는 사람도 있다. 따라서 기존 앱이 모두 나쁘다고 보면 안 된다.
- **정보가 부족한 경우:** 토스·뱅크샐러드·카드사 앱의 2026년 현재 카드별 정확도는 직접 사용하지 않았으므로 추가탐색 필요다.
- **아직 만들어지지 않은 것으로 보이는 부분:** 예상과 실제의 차이를 약관 문장·거래내역과 함께 묶어 이의제기를 준비하는 기능은 공개 설명에서 찾지 못했다.

### 3.7 데이터·API·인증·외부 실행 가능성

#### 상품 규칙 데이터

- [여신금융협회 카드상품 공시](https://gongsi.crefia.or.kr/portal/financialProdInfo/cardProd)는 상품 탐색의 출발점이 될 수 있으나, 혜택 적용 규칙은 각 카드의 상품설명서와 카드사 페이지를 함께 확인하라고 안내한다.
- 국내 모든 카드의 혜택·실적·제외항목을 동일 형식으로 주는 공개 무료 API는 이번 조사에서 찾지 못했다.
- MVP에서는 공개된 상품설명서가 있는 카드 세 개를 골라 규칙을 직접 구조화하는 것이 재현 가능하다. 실제 카드명을 쓰면 문서 버전과 적용일을 함께 저장해야 한다.

#### 실제 거래와 받은 혜택 데이터

- 카드사 앱의 거래·혜택 데이터를 범용 공개 API로 가져오는 방법은 찾지 못했다.
- 자동 통합은 금융 마이데이터 라이선스나 사업자 제휴가 필요한 영역이다. 공모전 MVP에서 이를 확보했다고 가정하면 안 된다.
- 사용자가 자신의 월 명세서 CSV·PDF·캡처를 업로드하는 방식은 자동연결보다 불편하지만, 무제휴 웹 MVP로 핵심 가치를 검증할 수 있다.
- 실제 포인트는 별도 적립내역에 있거나 며칠 뒤 반영될 수 있다. 데이터가 없으면 `누락`이 아니라 `반영 대기 또는 확인 필요`로 표시해야 한다.

#### 우리 웹사이트 안에서 가능한 실행 단계

1. 카드 규칙과 확인방법 제공: 가능
2. 정확한 카드사 혜택·상담 화면 연결: 카드사별 딥링크 안정성 확인 필요
3. 명세서 업로드와 거래·근거 정리: 가능
4. 기대 혜택과 실제 혜택 대사: 선택한 카드와 데이터 범위 안에서 가능
5. 카드사 상담창을 공식 임베드하거나 문의를 자동 접수: 공개 허용 근거 없음
6. 누락 혜택을 환급하고 결과를 수신: 카드사 권한이므로 불가능

즉, 최종 환급까지 하지 못해도 `어느 거래가 왜 의심되는지 찾기 → 근거 준비 → 정확한 공식 채널 열기`로 검색과 설명 단계를 줄일 수 있다.

### 3.8 세 개의 Mock 프로필

| 프로필 | 상황 | 데모에서 보여줄 핵심 |
|---|---|---|
| 할인 거래 착각 사용자 | 5만 원 결제에서 5천 원 할인받고 4만5천 원만 실적에서 제외된다고 생각 | 상품 규칙에 따라 결제 전액이 제외되는 경우를 거래와 원문 근거로 설명 |
| 생활비 카드 사용자 | 총 35만 원을 썼지만 관리비·세금·상품권 때문에 인정실적은 26만 원 | 총 사용액과 인정실적의 차이를 항목별로 분해하고 부족액 표시 |
| 혜택 누락 의심 사용자 | 실적을 채웠는데 통신비 청구할인이 보이지 않음 | 월 한도·자동이체 등록·매입 시점·실제 청구내역을 확인하고 문의문 생성 |

### 3.9 MVP 범위

- 카드 세 개의 합성 상품설명서 규칙 또는 공개 설명서에서 수작업 구조화한 규칙
- 세 프로필의 합성 거래명세서와 실제 혜택내역
- 거래별 `실적 인정 / 제외 / 판정 보류`와 근거 문장 표시
- 기대 할인·적립과 실제 혜택 비교
- `한도 소진 / 실적 부족 / 제외 업종 / 취소 반영 / 반영 대기 / 설명불가` 분류
- 설명불가 항목의 거래·약관·질문을 묶은 카드사 문의 초안
- 실제 카드·거래 연결은 하지 않고, 화면에 Mock임을 명확히 표시

### 3.10 AI가 꼭 필요한가

핵심 실적·혜택 계산은 버전이 고정된 규칙 엔진으로 처리해야 한다. AI의 적절한 역할은 다음이다.

- 긴 상품설명서에서 혜택 조건·예외·한도 후보를 뽑아 사람이 검수하도록 지원
- 명세서 PDF나 캡처의 서로 다른 표현을 공통 거래 형식으로 변환
- 판정 근거와 문의문을 사용자가 이해하기 쉽게 설명

AI가 최종 혜택 누락이나 환급 가능성을 단정해서는 안 된다. 업종코드와 카드사 내부 판정정보가 없으면 `확인 필요`가 정답일 수 있다.

### 3.11 해외 벤치마크

[MaxRewards](https://maxrewards.com/)는 여러 카드사의 잔액·리워드·혜택·오퍼·보너스 진행도를 한 앱에 모으고, 결제 시 가장 유리한 카드를 추천한다. 공식 페이지는 900개 이상 카드의 구조화된 데이터와 혜택 추적을 설명한다.

이 사례는 카드 규칙을 구조화해 지속적으로 관리하는 제품이 가능하다는 점을 보여준다. 그러나 공개 설명상 핵심은 혜택 최적화와 추적이지, **받았어야 할 혜택과 실제 혜택을 거래별로 감사해 이의제기 증빙을 만드는 것**은 아니다. 국내 후보는 그 사후 확인에 초점을 맞춰야 한다.

### 3.12 추가 확인이 필요한 질문

1. 실제 카드 명세서에 혜택 금액과 거래 연결 식별자가 어느 수준으로 제공되는가?
2. 카드사별 승인일·매입일·청구일·취소 반영 규칙을 공개 문서만으로 계산할 수 있는가?
3. 가맹점 업종코드를 사용자가 받는 명세서에서 알 수 없을 때 오판을 어떻게 줄일 것인가?
4. 카드 세 개의 규칙을 유지하는 비용과 규칙 변경 감지 방식을 감당할 수 있는가?
5. 사용자가 원하는 것은 다음 달 실적 관리인지, 지난달 혜택 누락 확인인지 인터뷰로 구분해야 한다.
6. 카드사 상담에 제공할 문서가 실제 상담시간과 왕복 설명을 얼마나 줄이는지 확인해야 한다.

## 4. 두 신규 후보를 같은 언어로 비교

| 관점 | 판매자 정산 차이 감사 | 카드 혜택 누락 감사 |
|---|---|---|
| 주 사용자 | 여러 온라인몰을 운영하는 소규모 판매자 | 복수 혜택카드를 쓰는 개인 |
| 반복 사건 | 주문·취소·반품·정산·입금 | 매월 결제·실적·할인·적립 |
| 커뮤니티에서 보인 행동 | 엑셀 대사, 세무·정산 질문, 고객센터 문의 | 카드사 앱 재확인, 수동 제외, 커뮤니티 질문 |
| 가까운 기존 제품 | 셀러봇캐시, DashPanda, ERP | 카드사 앱, 뱅크샐러드, 토스, 체리피커 |
| 피해야 할 중복 | 정산예정 달력, 단순 마진표, 주문통합 | 단순 실적계산, 카드추천, 자산통합 |
| 잠정적 빈틈 | 주문→정산→은행 입금의 설명 가능한 감사와 문의증빙 | 기대 혜택→실제 혜택의 거래별 감사와 문의증빙 |
| 무제휴 MVP 입력 | 플랫폼 정산 CSV + 은행 CSV | 상품 규칙 + 명세서 CSV/PDF/캡처 |
| 자동연결 | 네이버·쿠팡 판매자 인증 API 일부 가능 | 마이데이터·카드사 제휴 없이는 어려움 |
| 우리 웹 안의 현실적 상한 | 대사·차이설명·문의자료 생성 | 판정·혜택대사·문의자료 생성 |
| 외부 권한이 필요한 마지막 단계 | 정산 수정·지급·문의 접수 결과 | 혜택 환급·카드사 판정·문의 결과 |
| 핵심 불확실성 | 기존 ERP·정산서비스가 이미 어디까지 대사하는가 | 명세서만으로 실제 혜택과 업종 판정을 얼마나 정확히 복원하는가 |

## 5. 지금 단계의 결론

### 판매자 정산 후보

문제의 실재성은 강하다. 서로 다른 플랫폼을 쓰는 판매자가 매출·정산·입금을 다시 엑셀로 맞춘다는 사례가 반복된다. 반면 정산 달력과 마진분석 시장은 이미 존재하므로, 제품 범위를 `주문-정산-실입금의 차이 감사`보다 넓히면 금방 기존 서비스와 겹친다. 두 플랫폼의 판매자용 정산 API가 공개돼 있어 자동연결의 일부도 현실적이지만, MVP는 파일 업로드만으로 검증할 수 있다.

### 카드 혜택 후보

문제의 반복성과 사용자 언어가 분명하고, 더쎈카드 종료 뒤 대체재를 찾는 현재 수요도 보인다. 그러나 실적 계산과 카드추천 제품은 이미 많다. 따라서 `혜택 누락 의심 건을 거래·약관과 함께 찾아 문의를 준비한다`는 사후 감사로 좁혀야 한다. 자동 거래연결의 권한 장벽은 판매자 후보보다 높으며, 명세서에 필요한 데이터가 충분한지가 가장 큰 검증 과제다.

두 후보 모두 최종 돈의 지급이나 환급을 우리 서비스에서 완료하지 못한다. 그래도 사용자가 현재 수작업으로 하는 **발견 → 대조 → 원인 추정 → 근거 준비 → 공식 채널 이동** 중 앞의 네 단계를 줄일 수 있다. 다음 토론에서는 최종 성공 기준을 미리 고정하기보다, 실제 사용자 자료 한 건을 받아 수작업으로 끝까지 대사해 본 뒤 어떤 단계가 가장 오래 걸리는지 확인하는 편이 적절하다.
