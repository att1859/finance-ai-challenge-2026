# 2차 조사 — 세 후보 비교와 다음 논점

- 조사 기준일: 2026-08-15
- 비교 대상: 소상공인 정책자금 / 정기결제 발견·해지·환불 / 맞춤형 복지·금융지원
- 원칙: 이 문서는 점수표나 최종 순위가 아니다. 현재 확인된 문제, 기존 해결, 실행권한, 불확실성을 같은 언어로 놓고 토론하기 위한 자료다.

## 1. 세 후보를 한 문장으로 다시 정의

| 후보 | 처음 생각한 문제 | 2차 조사 뒤 더 정확해진 문제 |
|---|---|---|
| 소상공인 정책자금 | 내게 맞는 정책자금을 찾고 신청하기 어렵다 | 공고는 이미 많지만 자금·기관을 구분하고, 적격 가능성과 금융심사를 분리하며, 공단→보증기관→은행의 서류와 진행을 이어가기 어렵다. |
| 정기결제 | 흩어진 구독을 발견하고 해지·환불하기 어렵다 | 발견 이후에도 모호한 가맹점명, 가입 채널, 해지와 환불의 분리, 누락된 결제, 처리상태 때문에 올바른 주체를 찾아 반복 이동한다. |
| 맞춤형 지원 | 내게 맞는 복지·금융지원을 찾아 신청하기 어렵다 | 맞춤검색은 이미 정부24·복지로·온통청년에 있지만 수록 범위·판정항목·신청권한이 달라 중앙·지역·대상별 포털을 다시 연결해야 한다. |

## 3. 단계별 여정 비교

| 공통 단계 | 정책자금 | 정기결제 | 맞춤형 지원 |
|---|---|---|---|
| 발견 | 공고·자금 종류 찾기 | 반복 결제 찾기 | 중앙·지역·대상별 혜택 찾기 |
| 식별 | 직접/대리대출, 공단/보증/은행 구분 | 가맹점명을 실제 서비스·가입채널로 변환 | 같은 혜택의 중복, 중앙/지방/기관 구분 |
| 자격·가능성 | 업력·업종·매출·신용·체납 | 해지 가능, 환불 가능, 청구 주체 | 연령·지역·소득·재산·가구·과거수혜 |
| 준비 | 기관별 서류·인증·사업정보 | 날짜·금액·영수증·미사용 여부 | 서류·가구원 동의·인증수단 |
| 실행 | 공단→보증기관→은행 | 서비스·Apple·Google·통신사·카드 | 정부24·복지로·온통청년·지자체 |
| 결과 | 접수·확인서·보증·은행 승인 | 해지 완료·환불 결과·재청구 | 접수·보완·수급결정 |
| 재탐색 | 새 공고·예산·사업상태 변화 | 새 구독·결제수단·정책 변화 | 소득·가구·거주·제도 변화 |

세 후보 모두 “정보를 한 번 알려주면 끝”이 아니다. 반면 최종 실행의 권한은 외부 기관이나 사업자가 가진다. 그러므로 팀이 소유할 수 있는 구간은 대체로 **발견→식별→준비→정확한 공식 경로 연결→사용자 중심 상태관리**다.

## 4. 실행 단계 1~6 비교

### 단계 정의

1. 정보만 제공
2. 정확한 외부 신청·해지 링크
3. 입력·서류·증빙 준비
4. 외부 화면과 나란히 안내
5. 공식 임베드 또는 일부 실행
6. 우리 서비스에서 완료하고 결과 수신

| 후보 | 무제휴로 현실적인 상한 | 조건부 가능 | 파트너십이 필요한 구간 | 현재 공개 근거상 불가능한 약속 |
|---|---|---|---|---|
| 정책자금 | 3 + 공고별 2 | API의 신청 URL 품질과 딥링크 안정성이 확보되면 2 강화 | 공단 신청, 신용·부채 확인, 보증·은행 상태 연계 | 우리 사이트에서 대출 신청부터 입금까지 완료 |
| 정기결제 | 3 + Apple·Google·사업자별 2 | 업로드 명세서 분석, 일부 공식 자동납부 해지 경로 | 금융거래 자동수집, 가맹점 직접해지, 환불 상태 콜백 | 모든 구독을 한 버튼으로 해지·환불 |
| 맞춤형 지원 | 3 + 온통청년 등 일부 2 | 정부24 API의 신청 URL 필드 품질 확인 후 2 확대 | 정부24·복지로·지자체 신청 임베드, 결과 연계 | 전국 모든 혜택을 우리 사이트에서 신청 완료 |

PiP와 외부 화면 동시 안내는 현재 보류한다. iframe은 세 후보 모두 공식 허용 근거를 찾지 못했으며, 인증 페이지는 보안 헤더와 세션 정책 때문에 동작하지 않을 가능성이 높다. 딥링크와 준비 체크리스트를 우선 검증하는 편이 현실적이다.

## 6. 기존 서비스가 있는데도 생기는 네 종류의 틈

### 6.1 인지도 틈

사용자가 공식 서비스를 모른다. 그러나 이것만 해결하면 홍보·링크 모음에 그칠 수 있다.

### 6.2 사용성 틈

로그인·인증·반복입력·모바일 화면·접근성 때문에 중간에 이탈한다. 앱스토어 리뷰와 사용자 질문에서 반복되지만 직접 사용성 테스트는 아직 하지 않았다.

### 6.3 기능 틈

서비스가 발견은 해도 준비·실행·결과를 이어주지 않는다. 세 후보의 공통 핵심이다.

### 6.4 권한 틈

기능을 만들 능력이 아니라 법적·기술적 권한이 없어서 실행할 수 없다. 공단·은행, 금융 마이데이터, 가맹점·공공기관의 인증과 결과 API가 여기에 해당한다.

제품 아이디어는 기능 틈을 겨냥하되 권한 틈을 기능 부족으로 오인하지 않아야 한다.

## 8. 커뮤니티에서 새로 찾은 두 후보

기존 세 후보의 기능을 옆으로 확장한 `지원 신청 준비지갑`과 `지원조건 변경·재자격 알림`은 신규 아이디어에서 제외했다. 새 조사는 공문·뉴스가 아니라 국내 커뮤니티 질문과 앱 리뷰에서 반복되는 수작업을 출발점으로 삼았다. 상세 근거와 링크는 [2차_조사_신규아이디어.md](./2차_조사_신규아이디어.md)에 정리했다.

### A. 멀티채널 판매자의 주문·정산·실입금 차이 감사

스마트스토어·쿠팡·ESM·자사몰의 주문금액, 수수료·쿠폰·반품, 정산예정액과 실제 은행 입금액을 주문 단위로 맞추고 차이의 이유를 설명한다.

- 커뮤니티에서는 매출과 입금이 맞지 않아 정상적인 정산 시차인지 모르는 질문, 주문별 정산 확인용 엑셀을 직접 만드는 사례가 반복됐다.
- 셀러봇캐시·DashPanda·판매 ERP가 이미 정산예정과 마진·주문 통합을 제공하므로 단순 대시보드는 중복이 크다.
- 남는 빈틈은 `주문 → 플랫폼 정산 → 실제 입금`을 연결해 정상 차이와 설명불가 건을 나누고 고객센터 문의 근거를 만드는 흐름이다.
- 네이버·쿠팡은 판매자 인증형 정산 API가 있고, 제휴 없는 MVP는 플랫폼 CSV와 은행 CSV 업로드로 가능하다.
- 플랫폼이 지급액을 수정하거나 문의 결과를 돌려주는 마지막 실행은 공개 API 범위가 아니다.

### B. 카드 혜택 누락 감사와 문의 준비

카드 상품설명서와 월 거래내역을 비교해 받았어야 할 할인·적립과 실제 혜택의 차이, 전월실적 제외 이유를 거래별로 설명한다.

- 사용자들은 실적을 채웠다고 생각했는데 할인이 없거나, 할인 거래·관리비·세금·취소가 실적에서 어떻게 빠지는지 반복해서 묻는다.
- 카드사 앱, 뱅크샐러드, 토스, 체리피커가 있어 단순 실적조회·카드추천은 중복이 크며, 더쎈카드 종료 뒤 대체재를 찾는 글도 이어졌다.
- 남는 빈틈은 `예상 혜택 → 실제 혜택`을 대사해 한도·제외·반영시차·설명불가로 나누고 약관과 거래가 포함된 문의자료를 만드는 흐름이다.
- 국내 전체 카드 규칙과 거래를 주는 공개 무료 API는 찾지 못했다. MVP는 카드 세 개의 규칙과 사용자 명세서 업로드로 제한해야 한다.
- 자동 거래통합은 마이데이터·카드사 제휴가 필요하고, 환급과 최종 판정은 카드사 권한이다.

## 9. AI 사용을 아직 전제로 하지 않는 공통 원칙

- 구조화된 연령·지역·기간·금액 조건은 규칙 기반으로 처리한다.
- AI는 긴 공고·환불정책의 예외 추출, 서로 다른 명칭의 중복 판별, 사용자 질문 생성처럼 비정형 작업에만 후보로 둔다.
- 결과에는 원문 출처, 규칙 판정, AI 해석, 미확인 항목을 분리한다.
- 대출 승인, 환불 승인, 복지 수급을 AI가 단정하지 않는다.
- AI가 없어도 사용자 단계가 실제로 줄어드는 구조를 먼저 확인한다.

## 10. 아직 결정하지 않은 것

사용자 요청대로 이 단계에서 고정 점수나 성공 기준을 만들지 않았다. 다음 항목은 아이디어를 더 좁힐 때 확인할 사실이지, 지금 후보를 기계적으로 탈락시키는 배점표가 아니다.

- 공개 API의 실제 데이터 품질과 누락률
- 정확한 딥링크가 세션 없이 유지되는 비율
- 사용자가 가장 오래 머무는 단계가 탐색·식별·준비 중 어디인지
- 민간 기존 서비스의 실제 사용자 수와 이탈 이유
- 기관 파트너십 없이 만들 수 있는 데모가 문제를 충분히 보여주는지
- 민감정보를 저장하지 않아도 핵심 경험을 구현할 수 있는지

## 11. 기관별 확인 질문 묶음

### 공통

1. 제3자 서비스의 공고·상세·신청 링크 재사용 조건은 무엇인가?
2. 딥링크·위젯·iframe·연계로그인 중 공식 지원 방식이 있는가?
3. 신청 결과나 보완요청을 사용자 동의 아래 받을 수 있는가?
4. 개발용 샌드박스나 Mock 데이터가 있는가?
5. 공식 데이터의 수정·폐지·마감 상태를 증분으로 받을 수 있는가?

### 정책자금

- 공단·보증기관·은행의 중복서류와 결과 연계 가능성
- 신청 URL 안정성, 확인서와 승인 상태의 기계적 구분

### 정기결제

- 금융보안원 기반 구독관리 서비스의 제공 데이터와 참여사
- 어카운트인포의 해지 대상, 가맹점 회원계약과 자동납부 해지의 관계
- 가맹점 직접 해지·환불 상태 API 존재 여부

### 맞춤형 지원

- 정부24 API의 신청 URL·수정일·지역 데이터 품질
- 복지로 온라인 신청 가능 여부를 데이터에서 구분하는 방법
- 온통청년 API 승인과 신청 URL 재사용 조건

## 12. 토론할 때 놓치지 말아야 할 사실

- **정책자금:** 공개 공고 데이터와 신청 URL이 있어 준비형 MVP는 만들 수 있지만 최종 금융 실행은 다기관 심사다.
- **정기결제:** 사용자 고통은 구체적이지만 왓섭과 정부 추진안이 매우 가까우며 자동 발견의 핵심 데이터는 허가·제휴 영역이다.
- **맞춤형 지원:** 공개 API가 풍부하지만 단순 개인화는 이미 정부24+가 하고 있다. 중앙·지역·대상별 실행 경계를 연결해야 새 가치가 생긴다.
- 세 후보 모두 “우리 사이트 안에서 끝까지”를 무리하게 약속할 필요는 없다. 단계 2와 3을 정밀하게 만들고 외부 이동 횟수와 준비 누락을 줄이는 것 자체가 검증 가능한 가치다.
