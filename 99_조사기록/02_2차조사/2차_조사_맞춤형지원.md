# 2차 조사 — 받을 수 있는 복지·금융지원의 발견과 신청

- 조사 기준일: 2026-08-13
- 변형된 아이디어: 모든 제도를 새로 수집하는 서비스가 아니라, 사용자의 최소 프로필에 맞춰 정부24·복지로·온통청년·지역 플랫폼을 연결하고 자주 쓰는 지원은 우리 화면에서도 준비 정보를 제공하는 “지원 서비스 메타 탐색기”
- 조사 방식: 실제 개인정보나 허위 정보를 입력하지 않고 공개 페이지·공개 API·앱스토어 사용자 반응으로 여정과 구현 경계를 재구성

## 1. 먼저 드러난 결론

“서울에 사는 청년에게 온통청년과 서울 지원 사이트를 연결한다”는 방향은 이해하기 쉽지만, **개인화 검색 자체는 이미 정부 서비스와 크게 겹친다.**

- [정부24+ 혜택알리미](https://plus.gov.kr/portal/benefitV2)는 개인화 알림, 가족 정보, 간편찾기, 생애상황별 혜택을 제공한다.
- [복지멤버십](https://www.bokjiro.go.kr/ssis-tbu/twatza/wmAplyMng/selectWmGdnc.do)은 연령·가구·소득재산을 분석해 받을 가능성이 있는 복지서비스를 정기 안내한다.
- [온통청년](https://www.youthcenter.go.kr/)은 청년정책을 지역·분야로 검색하고 로그인 후 맞춤정책과 스크랩을 제공한다.
- [청년몽땅정보통](https://youth.seoul.go.kr/mainA.do)은 서울시·취업상태·연령 기반 맞춤검색과 일부 정책 통합신청을 제공한다.

그럼에도 빈틈은 남아 있다. 정부24, 복지로, 중앙·지역 청년 플랫폼은 **수록 범위, 최신성, 자격판정에 쓰는 항목, 신청 가능 범위, 인증 방식**이 다르다. 특히 복지로 앱의 공식 답변은 중앙정부 복지는 온라인 신청할 수 있지만 지자체 복지는 정보만 제공되고 해당 지자체에서 신청해야 하는 경우가 있음을 확인해준다.

따라서 제품 가치가 생기려면 “맞춤형 혜택 목록”보다 다음에 집중해야 한다.

1. 같은 사용자에게 어떤 공식 사이트가 각각 무엇을 알고 있는지 보여준다.
2. 중복 제도와 비슷한 이름을 합치고 출처·수정일을 표시한다.
3. “가능성 있음 / 추가정보 필요 / 공식 확인 필요”를 분리한다.
4. 필요한 서류와 정확한 신청처를 준비해 외부 실행의 검색 피로를 줄인다.
5. 중앙·지역 서비스의 정보만 있고 신청은 다른 곳인 단절을 명시한다.

## 2. 사용자 여정별 문제

| 1. 출발점 찾기 | 정부24·복지로·온통청년·지자체 중 어디서 시작할지 결정 | 대상과 기관에 따라 포털이 다르고 같은 혜택이 여러 곳에 나타남 | 온통청년과 청년몽땅정보통이 각각 전국·서울 청년정책을 별도로 운영 |

| 7. 신청 | 서류·동의·가구원 정보를 입력 | 인증서 가져오기, 반복입력, 모바일 접근성 문제가 남음 | 복지로 앱의 2026-05 인증서 오류 리뷰, 2026-02 장애 사용자 접근성 리뷰 |
| 8. 변화 추적 | 소득·가구·거주지 변화 후 새 혜택 확인 | 한 번 검색으로 끝나지 않고 상황변화와 공고 마감에 따라 재판정 필요 | 복지멤버십은 월별 변동 탐지, 정부24는 맞춤 알림을 이미 제공 |

### 사용자 반응을 해석할 때의 주의

- 정부24 앱 리뷰의 상당수는 다른 민원·전자증명서 기능에 관한 내용이다. 여기서는 혜택 매칭 정확도의 근거가 아니라 **인증·세션·반복입력이라는 플랫폼 공통 장벽**으로만 사용했다.
- 복지로 앱 리뷰는 중앙정부와 지자체 서비스의 신청 범위가 다르다는 공식 답변이 붙어 있어 실행 단절의 근거로 가치가 높다.
- 앱스토어 평점은 버전·기기·이용목적이 섞이므로 문제 규모를 그대로 나타내지 않는다.

## 4. 공개 데이터와 API

### 행정안전부 대한민국 공공서비스(혜택) 정보

[공공데이터포털 상세](https://www.data.go.kr/data/15113968/openapi.do)에서 확인한 조건은 다음과 같다.

- 정부 부처, 지방자치단체, 공공기관, 교육청의 공공서비스 목록·상세·지원조건 제공
- REST, JSON/XML, 전국 범위
- 무료, 이용허락범위 제한 없음
- 개발·운영 모두 자동승인
- 개발계정 10,000회, 운영은 활용사례 등록 후 증량 신청 가능
- 엔드포인트: 공공서비스 목록, 상세내용, 지원조건

이 API는 전국 서비스 메타검색의 핵심 기반이 될 수 있다. 다만 상세 응답의 신청 URL·수정일·지역 서비스 누락률을 실제 샘플로 검증해야 한다. 공개 명세 페이지에서 목록·상세·조건 엔드포인트는 확인했지만, 모든 서비스에 안정적인 신청 URL이 들어 있다고 단정할 수는 없다.

### 온통청년 청년정책 API

[공공데이터포털](https://www.data.go.kr/data/15143273/openapi.do)은 무료, 개발 자동승인·운영 심의승인으로 안내한다. 실제 [온통청년 이용안내](https://www.youthcenter.go.kr/cmnFooter/openapiIntro/oaiGuide)는 회원가입, 인증키 신청, 담당자 심사 후 발급을 요구한다.

[제공목록](https://www.youthcenter.go.kr/cmnFooter/openapiIntro/oaiDoc)에서 확인한 주요 항목은 다음과 같다.

- 정책명·설명·분류·지역코드·주관/운영기관
- 지원내용·지원규모·선착순 여부
- 신청기간·신청방법·심사방법
- **신청 URL·참고 URL·제출서류**
- 최소·최대연령, 결혼상태, 소득조건, 취업·학력·전공·특화요건
- 최초등록·최종수정일

이 필드 구성이면 청년정책에 한해 **조건 매칭 → 이유 설명 → 제출서류 준비 → 정확한 신청 링크**를 만들 수 있다. API 안에 신청 제출 기능이나 결과 콜백은 없다.

### 데이터 간 충돌 주의

공공데이터포털은 온통청년 API를 JSON/XML로 표시하고, 온통청년 소개 페이지 본문은 XML 방식이라고 설명하지만 제공목록에는 `rtnType=json` 예시가 있다. 실제 키 발급 후 응답 형식을 확인해야 한다. 문서 간 표현 차이를 그대로 기록해두는 편이 안전하다.

## 5. 세 Mock 프로필로 본 포털 연결 구조

실제 신청 가능성을 확정하지 않고, 어떤 소스가 후보를 제공하며 어디서 다시 막히는지를 재구성했다.

| Mock 프로필 | 먼저 연결할 공식 소스 | 공개 데이터로 가능한 것 | 추가로 필요한 정보 | 예상 실행 단절 |
|---|---|---|---|---|

### Mock에서 확인된 제품 요구

- 사용자의 프로필 하나를 각 포털의 질문 형식으로 변환해야 한다.
- 같은 이름의 중앙·지역·민간 혜택을 중복 제거하되 출처는 유지해야 한다.
- 불확실한 항목이 있으면 후보를 숨기지 말고 “이 질문에 답하면 판정 가능”으로 보여줘야 한다.
- 38세 폐업 프로필처럼 복지와 소상공인 지원을 함께 보는 경우가 단일 공공 포털의 분류를 넘어선다.

## 6. 실행 단계별 현실성

| 단계 | 의미 | 현재 가능성 | 적용 |
|---|---|---|---|
| 1 | 정보만 제공 | 즉시 가능 | 정부24·온통청년 API와 공식 원문을 통합 |
| 2 | 정확한 외부 신청 링크 | 조건부 즉시 가능 | 온통청년은 신청 URL 필드가 있음. 정부24 공공서비스 API는 샘플별 URL 품질 검증 필요 |
| 3 | 입력·서류 준비 | 즉시 가능 | 프로필 질문, 자격 근거, 제출서류·기한 체크리스트, 외부 입력 전에 준비상태 확인 |
| 4 | 외부 화면과 나란히 안내 | 보류 | PiP는 보류. iframe 허용 근거도 없음 |
| 5 | 공식 화면 임베드·부분 실행 | 제한적/파트너십 필요 | 청년몽땅정보통·복지로·정부24가 자체적으로 일부 신청을 통합하지만 제3자 임베드 API는 확인하지 못함 |
| 6 | 우리 서비스에서 신청 완료·결과 수신 | 무제휴로 불가능 | 본인인증, 가구원·금융정보 동의, 전자서명, 기관 심사와 결과 API 필요 |

### 인증·개인정보 경계

- 정부24 간편찾기는 비로그인으로도 가능하지만 정확한 생년월일·성별·소득구간·지역을 요구한다.
- 개인화 알림과 가족정보는 로그인·동의가 필요하다.
- 복지멤버십의 정밀판정은 소득·재산과 금융정보 동의를 포함한다.
- MVP는 실제 주민등록·소득·재산을 자동조회하지 않고 세 Mock 프로필과 사용자가 고른 범주로 작동하게 할 수 있다.
- “받을 수 있음”이 아니라 “공개조건상 후보”, “정보 부족”, “공식 확인 필요”로 결과를 층화해야 한다.

## 7. 해외 벤치마크

### 캐나다 Benefits Finder

[Canada Benefits Finder](https://www.canada.ca/en/services/benefits/finder.html)는 필요한 지원 유형, 대상 집단, 주/준주를 선택해 연방 혜택을 좁힌다. 중요한 점은 **연방 혜택만 보여주고 지역 혜택은 주·준주 사이트 링크를 제공한다는 한계를 화면에 명시**하는 것이다.

이는 사용자가 말한 “호텔스컴바인처럼 공식 사이트를 연결”하는 국내형 구조와 가깝다. 모든 기관을 억지로 하나로 합치기보다 통합 범위와 외부 이동을 솔직히 표시한다.

### 영국 Benefits Calculators

[GOV.UK Benefits calculators](https://www.gov.uk/benefits-calculators)는 정부가 직접 하나의 계산기를 만드는 대신 무료·익명 민간 계산기 세 곳을 안내한다. 사용자는 저축, 본인·배우자 소득, 기존 급여, 임대료·보육비·지방세 정보를 준비한다. 계산 결과가 추정치이며 사용할 수 없는 집단도 명확히 고지한다.

국내에 가져올 점은 다음과 같다.

- 익명 또는 최소정보로 먼저 탐색하게 한다.
- 계산·매칭에 필요한 자료를 사전에 알려준다.
- 결과가 공식 수급결정이 아님을 분명히 한다.
- 더 전문적인 공식·민간 경로를 검증된 링크로 연결한다.

## 8. 팀이 줄일 수 있는 부분과 중복 위험

### 강하게 남아 있는 문제

- 중앙·지방·청년·소상공인 포털을 한 프로필에서 비교
- 같은 혜택의 중복 항목과 서로 다른 신청처 정리
- 데이터 출처·수정일·신청마감·지역 범위를 눈에 띄게 표시
- “왜 후보인지”와 “무엇을 더 알아야 하는지” 설명
- 신청 전 필요한 서류와 인증 수단을 한 번만 준비
- 정보만 제공되는 지자체 서비스를 실제 신청처로 정확히 연결

### 이미 해결에 가까운 부분

- 전국민 대상 기본 개인화 혜택 검색
- 생애상황·가족 기반 알림
- 청년정책의 지역·분야 검색
- 일부 중앙복지와 서울 청년정책의 온라인 신청

### 사용성이 좋다고 볼 수 있는 경우

- Government24+는 비로그인 간편찾기부터 시작할 수 있다.
- 온통청년은 공개 화면에서 지역·분야별 최신 정책과 신청마감일을 볼 수 있다.
- 청년몽땅정보통은 접수 중인 자체 정책을 별도로 모은다.

다만 이는 공개 화면 관찰이며 실제 로그인·신청 사용성은 직접 검증하지 않았다.

### 아직 만들어지지 않았다고 단정할 수 없는 경우

- 모든 지자체까지 포함한 중복 제거형 메타검색
- 여러 포털의 신청 준비상태를 하나로 관리
- 정부24·복지로·지역 사이트의 신청 결과를 한곳에서 추적

민간 서비스와 지자체 앱이 많아 추가 경쟁조사가 필요하다.

## 9. AI를 억지로 붙이지 않는 설계

- 연령·지역·기간·소득구간 같은 필드는 규칙 기반 매칭이 더 투명하다.
- AI가 유용할 가능성이 있는 곳은 비정형 자격조건의 구조화, 서로 다른 기관 문구의 중복 판별, 사용자의 자연어 상황을 추가 질문으로 바꾸는 작업이다.
- 각 결과에는 원문 출처, 마지막 수정일, 규칙으로 판정한 항목, AI가 해석한 항목을 분리해야 한다.
- AI가 복지 수급이나 금융지원 승인을 단정해서는 안 된다.

3. 지자체 공공서비스의 누락·중복·폐지 정보는 어떤 주기로 갱신되는가?

## 11. 현재 판단

이 후보는 단순 맞춤 추천으로 만들면 정부24+ 혜택알리미와 직접 겹친다. 더 설득력 있는 문제 정의는 **정부가 제공하는 여러 맞춤 서비스조차 범위와 실행권한이 달라 사용자가 다시 포털을 옮겨 다니며 조건·서류·신청처를 맞춰야 한다**는 것이다.

현실적인 MVP는 세 Mock 프로필에 대해 정부24 공공서비스 API와 온통청년 API를 결합하고, 중앙·지역·청년·소상공인 소스를 명확히 분리한 뒤, 후보마다 `근거가 충분함 / 추가정보 필요 / 공식 확인 필요`를 표시하는 방식이다. 실제 신청은 정확한 공식 딥링크로 넘기되, 이동 전에 필요한 서류와 인증수단을 준비하게 하면 단순 링크 모음 이상의 가치가 생긴다.
