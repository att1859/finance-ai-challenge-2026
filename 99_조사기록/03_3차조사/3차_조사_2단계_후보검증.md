# 3차 조사 2단계 후보검증 — S1·S2·C3

- 조사일: 2026-08-20
- 대상: S1 무역송금 계좌변경 가드, S2 투자사기 캠페인 지문 시스템, C3 재난 피해고객 선제지원 시스템
- 판단 기준: 기존 구현 수준, 한 단계 더 나갈 지점, 현실적인 정보 확보 방식, 웹 MVP에서 보여줄 실제 행동

## 0. 결론부터

| 후보 | 기존 서비스와 겹침 | 확인된 빈틈 | 가장 큰 실현 위험 | 판단 |
|---|---|---|---|---|
| S1 무역송금 계좌변경 가드 | **매우 큼**. 해외 제품은 이메일·문서·거래처 계좌 검증·결재 보류·ERP 연동까지 구현 | 국내 중소 무역기업이 ERP 없이 쓸 수 있는 경량형 흐름과 한국어·영어 인보이스 처리 | 해외 수취계좌 소유자를 우리 서비스가 독립 검증하기 어려움. 결국 비교·콜백 절차 도구로 축소될 수 있음 | **원안 제외, 국내 경량형 변형만 보류** |
| S2 투자사기 캠페인 지문 시스템 | 단건 식별자 조회, 스크린샷 판별, 음성·계좌 중심 군집화는 이미 존재 | 비정형 증거를 사건 타임라인으로 정규화하고, 기존 유형과 잘 맞지 않으면서 반복되는 흐름을 AI가 `임시 유형`으로 즉시 생성·추적하는 층 | 실제 신고 원문과 기관 간 데이터는 비공개. 허위 연결·개인정보·명예훼손 위험도 큼 | **사용자를 조사 담당자로 좁혀 유지** |
| C3 재난 피해고객 선제지원 시스템 | 재난 알림, 피해신고, 지원공지, 금융사 신청·심사는 각각 존재 | 피해자 신청 전에 재난지역·고객위치·상품·상환일을 연결해 `잠재 피해 케이스`를 여는 기관용 운영층 | 실제 고객·상품 데이터는 금융회사 내부에 있고, 위치만으로 실제 피해를 확정할 수 없음 | **조건부 유지** |

현재 세 후보 중 다음 프로토타입으로 가장 선명한 것은 **S2**다. AI가 맡을 비정형 증거 이해와 관계 추론이 분명하고, 결과도 `임시 유형 생성·신규 사건 자동 연결·우선순위 알림`이라는 즉시 행동과 `사건 병합·이관자료 생성`이라는 후속 행동으로 이어진다. **C3**는 사회적 가치와 화면 설득력이 좋지만 기관 내부데이터·업무 인터뷰가 필요하고, AI가 단순 부가기능으로 보일 위험이 있다. **S1**은 국내 문제는 크지만 해외에서는 이미 성숙한 제품 범주이므로 그대로 진행하기 어렵다.

> 이 문서의 `없음`은 시장 전체에 제품이 없다는 뜻이 아니다. 공개 제품 설명과 공식 안내에서 확인하지 못한 기능은 모두 `공개 확인 안 됨`으로 표기했다.

## 1. 공통 판단 원칙

세 후보 모두 최종 실행권한을 웹서비스가 직접 가진다고 과장하면 안 된다.

- S1은 은행 송금을 직접 막는 대신 서비스 내부 결재를 `보류`하고 재확인 과제를 연다.
- S2는 `임시 유형 생성·사건 자동 연결·담당자 알림`까지는 즉시 실행하되, 지급정지·공식 탐지룰 배포·대외 경고처럼 영향이 큰 조치는 담당자 승인 뒤 진행한다.
- C3는 위치 일치만으로 지원을 승인하지 않고 잠재 대상 케이스를 열어 연락·증빙 접수를 시작한다.

따라서 공통 MVP의 핵심은 `AI 판단 → 위험도에 맞는 업무 상태 변경 → 필요한 경우 사람 승인 → 감사로그 저장`이다. S2에서는 사람 확인이 모든 AI 활용의 선행조건이 되지 않도록 별도 설계한다.

# 2. S1 무역송금 계좌변경 가드

## 2.1 국내 문제는 실제로 충분히 크다

[한국무역협회가 전재한 금융감독원 집계](https://www.kita.net/board/totalTradeNews/totalTradeNewsDetail.do?no=95491&siteId=1)에 따르면 2021년부터 2025년 상반기까지 은행 송금 과정의 무역사기 피해는 1,591건, 9,584만 달러였고, 이메일 해킹을 통한 허위 계좌 송금 유도가 1,518건으로 95.4%를 차지했다. 피해업체 상당수는 상대방의 미입금 통보나 대금 독촉 뒤에야 사고를 알았다.

이 문제는 일회성 교육으로 끝나지 않는다. 공격자가 실제 거래 문맥·양식·회신 흐름을 재사용하고 매 지급 건마다 다른 인보이스와 계좌를 제시하기 때문이다. [ZeroAX의 국내 BEC 사고 분석](https://www.zeroax.com/blog/126640)도 유사 도메인, 계좌변경 요청, 반송 지연 서사, 위조 Wire/Vendor Form, 회신 체인 조작이 결합된 사례를 제시한다.

### 기존 서비스 수준에 대한 판단

해외에서는 `이메일/문서 → 거래처·계좌 검증 → 이상 탐지 → 승인 보류/차단 → ERP·TMS 연동`이 이미 하나의 성숙한 지급보안 제품군이다. 따라서 **기능 조합 자체는 차별점이 아니다.**

국내에는 BEC 이메일 보안, ERP 거래처계좌 통제, 국내 계좌 실명조회가 각각 존재한다. 다만 공개 설명 기준으로는 다음 흐름을 국내 중소 무역기업이 독립 웹서비스로 바로 쓰는 제품은 확인하지 못했다.

`메일·인보이스 업로드 → 과거 해외 거래계좌와 비교 → 위험 근거 제시 → 내부 결재 보류 → 기존 연락처 콜백 과제 → 확인 기록 후 해제`

이 빈틈은 제품 부재가 아니라 **보급·가격·구축 난이도·해외계좌 검증 범위의 빈틈**일 수 있으므로, 최종 아이디어로 올리기 전에 중소 수출입기업 재무담당자와 ERP 공급사 인터뷰가 필요하다.

## 2.3 한 단계 더 나갈 지점

### 버려야 할 차별화

- `AI로 피싱 메일을 탐지한다`: 국내외 이메일 보안제품이 이미 제공한다.
- `계좌가 바뀌면 알려준다`: ERP나 과거 지급내역의 단순 비교로 가능하다.
- `해외 계좌의 진짜 주인을 확인한다`: 검증 네트워크·은행 제휴 없이 신뢰성 있게 제공하기 어렵다.

### 남길 차별화 문장

> **ERP를 별도로 구축하기 어려운 국내 중소 무역기업을 위해, 다국어 메일·인보이스와 과거 지급이력을 비교하고 위험 시 내부 결재를 보류한 뒤 공격자가 제공하지 않은 기존 연락처로 재확인 과제를 강제하는 경량 지급통제 웹서비스.**

여기서 서비스가 보장하는 것은 `해외계좌의 진위`가 아니라 `변경·사칭 징후를 놓치지 않고 독립 채널 확인을 완료했다는 통제 증적`이다.

## 2.5 사용자 화면과 실제 행동

1. **지급 건 등록 화면**: 이메일·인보이스를 올리고 거래처를 선택한다.
2. **과거값 대조 화면**: 회사명, 계좌, 은행국가, 통화, 금액, 발신도메인, 납기조건을 이전 거래와 나란히 보여준다.
3. **위험 근거 화면**: `신규 계좌`, `수취계좌 국가 변경`, `유사 도메인`, `긴급·비밀 요청`, `회신체인 이상`을 근거별로 표시한다.
4. **결재 보류 화면**: 고위험 건을 `확인 필요`로 바꾸고 최종 승인 버튼을 잠근다.
5. **재확인 과제 화면**: 기존 연락처, 확인 질문, 담당자, 기한을 지정한다.
6. **해제·감사로그 화면**: 확인자, 확인채널, 결과, 첨부증빙과 해제 시각을 저장한다.

웹 MVP에서 실제로 작동시킬 행동은 `송금 보류 → 확인업무 배정 → 확인기록 제출 → 결재 해제`다. 은행 송금·실계좌 검증은 시뮬레이션으로 명확히 표시한다.

## 2.6 MVP 가능 범위

- 가상 거래처 5곳, 정상 인보이스 20건, 공격 시나리오 10건
- 한국어·영어 이메일, PDF 인보이스, 이미지 인보이스 지원
- 추출값은 AI, 계좌·금액·국가 변화는 규칙, 최종 해제는 사람 승인
- 데모 종료점: 위험 건을 정상 건과 구분하고, 보류된 결재를 재확인 기록 없이는 해제할 수 없음

### 판단: **원안 제외, 국내 경량형 변형만 보류**

국내 문제는 명확하지만 글로벌 중복이 너무 크고, 핵심처럼 보이는 해외 계좌 소유자 검증을 자체적으로 구현할 수 없다. 따라서 이메일·계좌검증·지급차단을 통합하는 **원래 S1은 기존 제품이 핵심 흐름을 이미 지원한다는 제외 기준에 해당한다.** `중소기업 경량 지급통제`라는 별도의 국내 변형은 보급 빈틈을 실무 인터뷰로 확인할 때만 다시 올리는 것이 타당하다.

### 즉시 제외 기준

- 국내 ERP·기업뱅킹이 중소기업에게 계좌변경 탐지·콜백·승인 보류를 낮은 비용으로 이미 제공한다.
- 해외계좌 검증이 없으면 재무담당자가 서비스를 신뢰하지 않는다는 인터뷰 결과가 나온다.
- EML/PDF 업로드만으로는 기존 업무보다 번거롭고 메일·ERP 연동 없이는 사용 의사가 없다.

### 기존 서비스 수준에 대한 판단

S2의 처음 표현인 `여러 플랫폼의 사기정보를 모아 AI로 유형화`는 부족하다.

- 전화·계좌 조회는 이미 널리 제공된다.
- URL·스크린샷 단건 AI 점검도 이미 있다.
- 음성으로 범죄조직을 군집화하는 수사모델도 있다.
- 전 금융권 계좌·피싱사이트·악성앱 정보를 공유해 실제 지급정지까지 연결하는 ASAP도 운영 중이다. 다만 2026년 1월 공개자료 기준 AI 공동모델과 위협지표 API는 아직 개발 중이므로, 현재 구현과 계획 기능은 구분해야 한다.

남는 지점은 **피해 신고의 비정형 앞단과 신종 수법의 조기 발견 사이**다. 피해자가 제출한 채팅 캡처, 가짜 수익 화면, 출금 거절 사유, 텔레그램·카카오톡 대화, 송금 내역, URL을 한 사건 타임라인으로 만들고, 공통 식별자가 없어도 진행 수법이 유사한 사건을 연결한다. 여기서 더 나아가 기존 유형과는 잘 맞지 않지만 서로 비슷한 사건 흐름이 반복되면 AI가 담당자 확정을 기다리지 않고 `임시 유형`을 만들어 이후 사건을 자동 연결하는 기능을 핵심으로 둔다.

## 3.2 주 사용자 결정

### 선택: 피해자가 아니라 `사건 접수·분석 담당자`

주 사용자는 금융회사 사기대응팀, 금융소비자보호·신고센터, 감독기관 접수·분석 인력, 플랫폼 신뢰·안전팀으로 잡는 것이 낫다.

피해자용 서비스로 만들면 이미 존재하는 조회·스크린샷 판별 앱과 겹치고, `사기 가능성이 높다`는 정보 제공으로 끝날 가능성이 높다. 담당자용으로 만들면 같은 분석 결과가 다음 상태변경으로 이어진다.

- 신규 사건 생성
- 기존 캠페인에 병합 또는 연결
- 반복되는 미분류 흐름의 임시 유형 생성과 신규 사건 자동 연결
- 임시 유형의 확산·중요도 알림
- 담당팀·관할 후보 배정
- 추가 증거 요청
- 계정·URL·거래기록 보전요청 목록 생성
- 수사기관·감독기관 이관자료 묶음 생성

피해자 화면은 `증거 업로드와 누락자료 안내`에 한정하고, 핵심 제품은 담당자 워크벤치로 둔다.

## 3.3 한 단계 더 나갈 지점

### 캠페인 지문의 구성

공통 전화번호·계좌번호가 없어도 다음 특징을 조합해 같은 캠페인 후보를 찾는다.

| 단계 | 추출할 특징 예시 |
|---|---|
| 유입 | SNS 광고, 지인·유명인 사칭, 무료 종목추천, 손실복구 제안 |
| 신뢰 형성 | 가짜 전문가·비서 역할, 단체방 수익 인증, 소액 수익 또는 출금 성공 |
| 투자 확대 | 전용 앱·가짜 거래소 설치, VIP방 승급, 대출·추가입금 유도 |
| 출금 봉쇄 | 세금·보증금·인증비·전산복구비 선납 요구, 미션 미완료 주장 |
| 운영 자산 | 유사한 사이트 화면, 도메인 패턴, 메신저 ID, 계좌, 전화, QR, 앱 파일 |
| 언어 지문 | 반복 문구, 역할명, 오탈자, 상담 시나리오 순서, 금액·비율 패턴 |

동일 식별자는 강한 연결, 수법·문구·화면 유사성은 약한 연결로 분리한다. 약한 연결만으로 `동일 범죄조직`이라고 확정하지 않고 `동일 캠페인 검토 후보`로 표시해야 한다.

### 자동 임시 유형과 담당자 권한의 분리

AI가 유형을 제안한 뒤 담당자가 건마다 승인해야만 분석이 시작되는 구조는 신종 수법 대응을 다시 늦춘다. 따라서 `업무용 임시 유형`과 `공식 범죄유형·외부 조치`를 분리한다.

1. AI가 증거를 표준 사건 타임라인으로 변환한다.
2. 기존 유형과의 적합도가 낮지만 내부 유사도가 높은 사건 흐름이 반복되면 임시 유형을 자동 생성한다.
3. 임시 유형에는 자동 이름, 공통 진행단계, 반복 문구·화면, 발생 건수, 기존 유형과의 차이, 연결 근거를 붙인다.
4. 생성 즉시 과거 사건을 다시 검색하고 이후 유입 사건을 자동 연결하며, 담당 큐의 우선순위와 알림을 갱신한다.
5. 담당자는 모든 사건을 사전 컨펌하지 않는다. 중요도가 높은 임시 유형을 합치기·나누기·기존 유형의 변종으로 편입하거나 공식 유형으로 확정한다.
6. 공식 탐지룰 배포, 계좌·사이트 차단 요청, 대외 경고 등 영향이 큰 후속조치만 담당자 승인을 필수로 한다.

임시 유형은 `새로운 범죄가 확정됐다`거나 `동일 조직이 저질렀다`는 판정이 아니다. 분석 속도를 높이기 위한 동적 작업 단위이며, 담당자 검토 전에도 사건 검색·연결·우선순위화 같은 내부 저위험 업무에는 바로 활용한다.

### 차별화 문장

> **피해자가 제출한 채팅·이미지·가짜 사이트·송금 과정을 사건 타임라인으로 만들고, 식별자가 달라도 반복되는 새로운 범행 흐름을 AI가 임시 유형으로 즉시 생성·추적하여 신종 수법을 알아차리는 시간을 줄이는 투자사기 분석 워크벤치.**

### 개인정보·명예훼손 방어 설계

- 결과를 일반 공개 검색 DB로 만들지 않고 권한이 있는 담당자 화면에만 표시한다.
- `범죄자`, `동일 조직` 대신 `연관 검토 후보`, `연결 신뢰도`를 사용한다.
- 전화·계좌는 기본 마스킹하고 업무상 필요한 권한에서만 원문을 본다.
- 임시 유형의 자동 생성·사건 연결 이력과 담당자의 병합·분리·확정·반려 이력을 모두 남긴다.
- 공개 경고는 별도 검증과 기관 권한이 있을 때만 가능하다고 명시한다.

## 3.5 사용자 화면과 실제 행동

1. **피해증거 접수 화면**: 채팅 캡처, 이체내역, URL, 가짜 앱·사이트 화면을 올린다.
2. **자동 사건 타임라인**: 유입 → 신뢰 형성 → 투자 확대 → 출금 봉쇄 순으로 사건을 재구성한다.
3. **증거 추출 화면**: 계좌·전화·도메인·메신저 ID·가짜 회사명·반복문구를 원문 위치와 함께 표시한다.
4. **연관사건 비교 화면**: 강한 식별자 일치와 약한 수법 유사성을 분리하고, 어떤 근거로 연결됐는지 보여준다.
5. **신종 패턴 레이더**: 기존 유형과 잘 맞지 않으면서 반복되는 사건군을 임시 유형으로 자동 생성하고, 공통 흐름·새로운 특징·발생 추이를 보여준다.
6. **캠페인 그래프**: 사건·식별자·사이트·수법 단계와 임시 유형의 관계를 시각화한다.
7. **담당자 행동 패널**: 자동 분석을 멈춰 세우지 않고 `임시 유형 합치기·분리`, `기존 유형의 변종`, `공식 유형 확정`, `담당 배정`, `추가증거 요청`, `이관자료 생성`을 처리한다.
8. **감사로그·이의검토 화면**: AI의 임시 유형 생성·자동 연결과 사람의 수정·확정 이력, 근거 파일을 저장한다.

웹 MVP의 실제 행동은 `증거 업로드 → 사건 구조화 → 반복되는 미분류 흐름 발견 → 임시 유형 자동 생성 → 신규·과거 사건 즉시 연결 및 알림 → 담당자의 고위험 후속조치 승인`이다.

## 3.6 MVP 가능 범위

### 데이터

- 합성 신고 40건, 알려진 유형 3개, 시간차를 두고 나타나는 신종 패턴 1개, 독립 사건 8건
- 채팅 이미지·가짜 투자화면·이체내역·신고 서술을 혼합
- 같은 캠페인 안에서도 계좌·전화·도메인을 일부 바꾸고, 진행 순서·문구·화면 요소만 재사용

### 모델·규칙 분담

- OCR·문서이해: 증거에서 개체와 사건단계 추출
- 임베딩·유사도: 문구·화면·진행수법 유사성 후보 생성
- 규칙: 동일 계좌·전화·도메인, 날짜 범위, 모순 체크
- 군집·이상탐지: 기존 유형과 잘 맞지 않지만 서로 닮은 사건을 임시 유형으로 생성하고 신규 사건을 지속 연결
- 그래프: 사건과 식별자·수법·임시 유형 관계 표현
- 사람 승인: 공식 유형 등록·탐지룰 배포·차단 요청·대외 경고 등 고위험 후속조치

### 성공 시연 장면

기존 유형과 잘 맞지 않는 신고가 시간순으로 유입된다. 일정한 반복성이 확인되는 순간 AI가 공통 진행단계·문구·가짜 화면을 근거로 임시 유형을 자동 생성하고 과거 사건을 재연결한다. 다음 신고부터는 담당자 확인을 기다리지 않고 같은 임시 유형으로 연결·알림하며, 담당자는 이후 공식화와 외부 조치만 결정한다.

### 판단: **변형해 유지 — 세 후보 중 1순위**

원래의 `범죄 형식 유형화`를 소비자 정보서비스로 두면 약하지만, `비정형 신고의 타임라인화 → 신종 패턴의 임시 유형 자동 생성 → 즉시 사건 연결 → 고위험 조치만 사람 승인`으로 좁히면 기존 단건조회·스크린샷 판별·음성군집·계좌공유 플랫폼과 경계가 생긴다. AI의 이점도 분류 편의가 아니라 **사람이 새로운 수법을 알아차릴 때까지의 지연을 줄이는 것**으로 선명해진다.

### 즉시 제외 기준

- 실제 담당자는 이미 내부 시스템에서 채팅·이미지·수법 기반 사건 병합을 충분히 수행한다.
- 합성 데이터에서 식별자 없는 사건 연결이 설명 가능하게 작동하지 않는다.
- 도입 대상 기관이 신고 원문을 외부 서비스에 처리시키는 것을 보안상 허용할 수 없고 온프레미스·폐쇄망 방식도 불가능하다.

# 4. C3 재난 피해고객 선제지원 시스템

## 4.1 현재 절차를 단계별로 정리

[금융위원회의 2026년 수해 금융지원안](https://www.fsc.go.kr/no010101/87566)은 피해 가계에 긴급생활안정자금, 대출 만기연장·상환유예, 보험료 납입유예·보험금 신속지급, 카드대금 청구유예, 특별 채무조정을 안내하고, 피해 소상공인·중소기업에는 긴급경영안정자금과 대출 만기연장·상환유예 등을 안내한다. [상세 첨부자료](https://www.fsc.go.kr/comm/getFile?srvcId=BBSTY1&upperNo=87566&fileTy=ATTACH&fileNo=2)는 지원 신청 전에 지자체의 재해피해확인서를 준비하도록 안내한다.

| 단계 | 현재 주체 | 현재 행동 | 끊기는 지점 |
|---|---|---|---|
| 1. 재난 발생·경보 | 행안부·산림청·지자체 | 재난상황·문자·피해지역 안내 | 금융회사의 고객·상품과 연결되지 않음 |
| 2. 사유재산 피해신고 | 피해자 → 지자체 | [국민안전24](https://www.safekorea.go.kr/) 또는 관할 지자체에 피해 신고 | 피해자가 신고경로와 기한을 알아야 함 |
| 3. 현장·서류 확인 | 지자체 | 피해를 확인하고 재해피해확인서 발급 | 발급 완료가 금융회사에 자동 전달된다고 공개 확인되지 않음 |
| 4. 금융지원 공지 | 금융위·금감원·금융회사 | 재난별 지원유형·기간·상담창구 발표 | 기관·업권별 문서가 분산되고 조건 표현이 제각각 |
| 5. 금융회사 신청 | 피해자 → 은행·카드·보험사 | 확인서와 필요서류를 제출하고 지원 신청 | 고객이 자기 상품에 가능한 지원을 찾아 개별 접수해야 함 |
| 6. 심사·실행 | 개별 금융회사 | 만기연장·상환유예·청구유예·보험금 처리 | 적용 조건과 승인 권한은 기관 내부에 있음 |

[행정안전부의 자연재난 피해신고 안내](https://www.mois.go.kr/frt/bbs/type002/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000205&nttId=119051)는 국민재난안전포털을 통한 온라인 신고를 안내한다. [BC카드의 산불피해 고객지원 안내](https://bccard.com/app/card/BcnewsViewActn.do?newsno=1559&newsurl=empty_url&linkTp=&listgo=1)도 피해지역 행정관청에서 피해사실확인서를 발급한 뒤 콜센터로 접수하는 흐름을 제시한다. 즉 공개 확인되는 중심 구조는 **피해자 신청형**이다.

### 피해자가 현재 지원을 찾기 쉬운가

`지원받을 길이 거의 없다`고 표현하면 부정확하다. 현재도 온라인 피해신고, 금융감독원 1332 상담, 금융업권별 상담창구, 피해지역 현장 금융상담이 마련된다. [2025년 산불 금융지원안](https://www.fsc.go.kr/no010101/84230)은 전 금융권 피해지원 금융상담센터 설치와 지원요청 우선처리를 명시하고, [2026년 수해 금융지원안](https://www.fsc.go.kr/no010101/87566)도 맞춤형 상담센터와 필요 시 현장 금융상담 인력 지원을 안내한다.

따라서 C3가 해결할 문제는 `피해자가 어디에서도 정보를 못 찾는다`가 아니다. 현재 절차의 남은 불편은 다음과 같다.

- 피해자가 먼저 피해신고를 하고 재해피해확인서를 받아야 한다.
- 그 뒤 자기 금융회사와 상품에 해당하는 지원을 확인하고 개별 신청해야 한다.
- 상담창구는 통합되어도 실제 심사·상태관리는 각 금융회사에 남는다.
- 금융회사가 신청 전 고객·상품·다가오는 상환일을 연결해 케이스를 여는지는 공개 확인되지 않았다.

즉 **정보 접근성은 생각보다 갖춰져 있고, 신청 전 기관 내부의 고객별 업무 생성이 미확인 빈틈**이다.

### 은행·카드·보험사가 이미 자동 선별·연락하는가

공개 지원 안내에서는 대체로 `피해사실확인서를 제출한 고객`, `콜센터 또는 영업점 접수`, `개별 심사`가 확인됐다. 이번 공개자료 조사에서는 재난 발생 직후 금융회사가 재난구역과 고객 위치·상품을 자동 대조해 신청 전 연락한다는 국내 상용제품이나 공통 시스템을 확인하지 못했다.

그러나 금융회사 내부 CRM에서 비공개로 수행할 가능성은 충분하다. 따라서 이는 `없는 기능`이 아니라 **공개 확인 안 됨·실무 인터뷰 최우선 항목**이다.

또한 `은행이 먼저 문자·전화로 대출을 권유한다`는 방향은 곤란하다. [2026년 수해 금융지원 상세자료](https://www.fsc.go.kr/comm/getFile?srvcId=BBSTY1&upperNo=87566&fileTy=ATTACH&fileNo=2)는 정부나 금융회사가 먼저 전화·문자·SNS로 재해피해 대출상품 가입을 권유하지 않는다고 안내한다. 재난지원 사칭 피싱을 막기 위한 원칙과 충돌하기 때문이다. 따라서 C3의 선제성은 **외부 대출권유가 아니라 은행 내부 케이스 개설과 인증된 앱 안의 지원안내**로 제한해야 한다.

## 4.3 한 단계 더 나갈 지점

### 버려야 할 범위

- 전국민 재난지원 통합검색: 기존 맞춤형 지원 후보와 겹친다.
- 위치만으로 피해자 자동 확정: 오판과 부당한 처리가 발생한다.
- AI가 대출 상환유예를 자동 승인: 금융회사 심사·내부통제 영역이다.
- 모든 재난·모든 업권 동시 지원: MVP가 얕아진다.

### 선택할 좁은 범위

**산불 × 소상공인 사업자대출 × 단일 은행**으로 좁힌다.

- 재난 입력: 산불 발생·영향 행정구역과 지원 공지
- 고객 입력: 합성 소상공인 사업장 주소, 대출상품, 원리금 납부일, 담당지점
- 판단: 재난지역 포함 여부, 가까운 상환일, 공개된 지원대상·필요서류
- 행동: 잠재 피해 케이스 생성, 담당지점 배정, 공식 앱 내 지원센터 노출 승인, 고객의 상담 요청 접수, 피해확인서 대기, 심사부서 이관

### 차별화 문장

> **산불 발생구역과 자사 소상공인 대출·상환일정을 연결해 잠재 피해고객의 내부 지원 케이스를 먼저 열고, 인증된 은행 앱에서 고객이 피해확인·상담을 시작하면 증빙과 상환유예 심사까지 이어주는 금융기관용 재난지원 운영 시스템.**

| 고객·사업장 위치 | 합성 고객 100명 | 금융회사가 이미 보유한 고객·사업자·담보 주소 | 개인신용정보·내부정보. GPS를 새로 수집하지 않고 기존 주소만 사용한다. [개인정보 보호법 제15조](https://www.law.go.kr/%EB%B2%95%EB%A0%B9/%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4%EB%B3%B4%ED%98%B8%EB%B2%95/%EC%A0%9C15%EC%A1%B0)의 추가이용 기준과 신용정보 규정에 대한 기관 내부 검토가 필요 |
| 대출·상환일정 | 합성 상품·납부일 | 은행 여신·CRM 시스템 | 실제 승인규칙이 아니라 연락 우선순위에만 사용 |
| 실제 피해여부 | 합성 확인서 | 고객 확인과 지자체 재해피해확인서 | 위치·사진만으로 자동 확정하지 않음. 확인서가 승인 전제 |
| 고객 안내·상담 | 인증된 앱 화면과 모의 푸시 | 은행 앱의 인증된 알림함·재난지원센터, 고객이 요청한 콜백 | 대출상품을 전화·문자·SNS로 먼저 권유하지 않는다. 링크·개인정보·송금을 요구하지 않고 고객이 공식 앱에 직접 접속해 확인하도록 설계 |

## 4.5 사용자 화면과 실제 행동

1. **재난 이벤트 화면**: 산불 위치·영향 행정구역·발생시각·공식 출처를 표시한다.
2. **지원공지 구조화 화면**: AI가 대상, 지원유형, 신청기간, 필요서류, 처리기관을 뽑고 담당자가 원문과 대조해 승인한다.
3. **잠재 피해고객 큐**: 사업장 위치, 대출상품, 다음 납부일, 담당지점, 선정 이유를 보여준다.
4. **고객 케이스 화면**: `앱 노출 전`, `고객 확인`, `피해 없음`, `상담 요청`, `확인서 대기`, `심사 이관` 상태를 관리한다.
5. **인증된 앱 안내 화면**: 고객별 가능한 지원과 확인서 발급경로를 은행 앱 안에 표시한다. 외부 문자에는 대출 권유·링크·개인정보 요청을 넣지 않는다.
6. **서류·이관 화면**: 확인서와 필요서류 체크리스트를 받고 적합한 지원부서로 넘긴다.
7. **운영 현황 화면**: 지역·지점별 고객 미확인, 확인서 대기, 상담·이관 건수를 보여준다.

웹 MVP의 실제 행동은 `재난 이벤트 생성 → 잠재 고객 선별 → 내부 케이스 개설 → 공식 앱 지원센터 노출 → 고객의 상담 요청 → 확인서 대기 → 심사 이관`이다.

## 4.6 MVP 가능 범위

### 데이터

- 과거 산불 한 건을 바탕으로 만든 행정구역 이벤트
- 합성 소상공인 100명, 사업장 주소, 대출 3종, 다음 납부일
- 공개 금융지원 공지 3건과 합성 은행 내부 지원규칙 1건
- 합성 재해피해확인서 5건

### AI와 비AI의 역할

- AI: 비정형 지원공지에서 대상·지원유형·기간·서류 추출, 인증된 앱 안내문 초안, 피해서술 요약
- 규칙·GIS: 행정구역 매칭, 납부일까지 남은 기간, 우선순위, 상태전환
- 사람: 지원규칙 승인, 앱 노출 승인, 피해 확인, 최종 금융지원 심사

### 성공 시연 장면

산불 이벤트가 들어오자 영향 행정구역의 소상공인 중 14일 안에 원리금 납부가 있는 고객이 우선 큐에 올라온다. 담당자가 지원공지의 근거문장을 확인해 내부 케이스를 열면 해당 고객의 공식 은행 앱에 재난지원센터가 나타나고, 고객이 상담을 요청한 뒤 확인서 제출 상태까지 관리한다.

## 4.7 약점 추가 검증 결과

| 약점 | 추가 확인 결과 | C3에 미치는 영향 |
|---|---|---|
| 현행 지원이 이미 충분히 쉬운가 | 온라인 피해신고, 1332, 전 금융권 상담센터, 현장 금융상담까지 존재 | `지원정보를 쉽게 찾게 해준다`는 문제정의는 약하다. 기관 내부의 고객별 케이스 생성으로 초점을 옮겨야 함 |
| 금융사가 이미 먼저 찾는가 | 공개 자료는 피해확인서 제출·콜센터/영업점 신청을 반복 안내하며, 재난구역·고객·상품 자동 대조 시스템은 확인하지 못함 | 잠재적 빈틈은 남지만 내부 비공개 기능일 수 있어 실무 인터뷰 없이는 존재를 단정할 수 없음 |
| 선제 연락이 안전한가 | 금융위는 정부·금융회사가 먼저 전화·문자·SNS로 재해대출 가입을 권유하지 않는다고 경고 | 전화·문자 중심 원안은 약점. 인증된 은행 앱 내 안내와 고객 요청형 상담으로 바꿔야 함 |
| 재난 데이터가 피해를 증명하는가 | 실시간 발생 위치·상태는 볼 수 있지만 공개 데이터가 개별 사업장의 실제 피해를 증명하지는 못함 | 고객은 `피해자`가 아니라 `잠재 영향 고객`으로만 분류하고 지자체 확인서를 기다려야 함 |
| 주소정보 활용이 쉬운가 | 은행은 고객·사업장 주소를 보유하지만 재난지원 목적으로 추가 이용 가능한지는 합리적 관련성·예측가능성·불이익·안전조치 등의 검토가 필요 | GPS 신규수집은 제외하고 기존 사업장 주소만 사용. 실제 도입 전 법무·개인정보 담당 승인 필요 |
| 외부 웹서비스로 배포하기 쉬운가 | 고객주소·대출상품·상환일은 은행 핵심 내부정보라 외부 SaaS로 반출하기 어렵다 | 공모전은 합성 데이터 웹 MVP로 가능하지만 실제 제품은 은행 내부망·전용 배포 또는 은행과의 제휴가 필요 |
| AI가 꼭 필요한가 | 지역·상환일 매칭과 케이스 생성은 규칙·GIS·CRM으로 가능 | 가장 큰 약점. 비정형 지원공지의 조건을 상품별 실행규칙으로 바꾸는 정확도·시간절감을 입증하지 못하면 제외해야 함 |

추가 검색 결과 C3의 핵심은 `은행이 먼저 연락한다`가 아니라 **은행이 먼저 내부 지원 케이스를 준비하되, 고객과의 접점은 인증된 앱에서 안전하게 시작한다**로 수정하는 것이 타당하다.

### 판단: **조건부 유지 — 세 후보 중 2순위**

기존 시스템의 분절이 분명하고 기관용 화면·행동도 선명하다. 공개·합성 데이터만으로도 핵심 흐름은 시연할 수 있다. 다만 피해자의 정보 접근 문제는 이미 상당 부분 보완되어 있으므로, **단순 안내 서비스로는 가치가 약하다.** 실제 도입가치는 금융회사가 이미 같은 선별을 내부에서 하는지, 기존 주소정보를 재난지원에 활용하고 인증된 앱에서 고객별 케이스를 노출할 수 있는지에 달려 있다.

또한 AI 역할이 지원공지 구조화에만 머물면 `AI를 붙인 GIS/CRM`으로 보일 수 있다. 여러 기관의 복잡한 비정형 공지를 고객 상품과 정확히 연결해 **담당자가 실제 케이스를 여는 시간과 누락을 줄이는 것**을 검증해야 한다.

### 즉시 제외 기준

- 은행이 이미 재난구역·고객위치·상품·상환일을 자동 연결해 신청 전 케이스를 여는 내부 기능을 운영한다.
- 공개 재난데이터의 위치·갱신속도가 선제 연락 후보를 만드는 데 너무 부정확하다.
- 기존 고객주소를 잠재고객 선별에 쓰거나 인증된 앱에서 지원 케이스를 노출하는 것이 법적·운영상 허용되지 않는다.
- 제품의 효용이 `재난지원 공지와 1332 상담을 다시 보여주는 것`에 그친다.
- 지원공지 구조화가 단순 템플릿 규칙으로 충분해 AI의 실질 역할과 검증지표를 만들기 어렵다.

## 추천 방향

1. **S2를 1순위로 프로토타입 후보에 둔다.** 제품 문장은 `투자사기 조회`나 `기존 유형 자동 분류`가 아니라 `비정형 신고 타임라인화·신종 패턴 임시 유형 생성·실시간 사건 연결`로 고정한다.
2. **C3를 2순위로 둔다.** 금융회사 재난지원 담당자 인터뷰 한 번만 확보돼도 실제 중복과 연락 권한을 빠르게 판별할 수 있다.
3. **S1 원안은 제외하고 당장 제작하지 않는다.** 국내 중소기업의 도입 빈틈과 해외계좌 검증 없이도 쓸 의향이 확인될 때만 경량형 변형을 별도 후보로 되살린다.

이 순서는 최종 공모전 우승 가능성을 점수화한 것이 아니라, 현재 조사에서 **기존 서비스와 다른 한 문장·AI의 핵심성·웹 MVP의 실제 행동**이 얼마나 분명한지를 기준으로 한 작업 우선순위다.
