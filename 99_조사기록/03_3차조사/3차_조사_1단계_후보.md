# 3차 조사 1단계 후보: 금융보안·새로운 금융 실행 기능

작성일: 2026-08-20  
범위: 금융보안 3개, 새로운 금융 기능 3개  
목적: 최종 아이디어 선정이 아니라, 팀이 2단계 심층조사 대상을 고를 수 있을 정도로 문제·사용자·행동·기존 서비스·MVP 가능성을 확인하는 것

## 0. 먼저 읽을 결론

이번 조사에서 중요한 구분은 **정보를 보여주는 서비스**와 **업무 상태를 실제로 바꾸는 서비스**다. 아래 후보는 모두 경고·보류·사건 병합·점검 반려·업무 배정·신청 준비 같은 다음 행동을 포함하도록 좁혔다.

| 구분 | 후보 | 핵심 사용자 | 서비스가 바꾸는 실제 상태 | 1단계 판단 |
|---|---|---|---|---|
| 보안 S1 | 무역송금 계좌변경 가드 | 수출입기업 재무·결재자 | 송금 보류, 별도 채널 확인업무 생성 | **2단계 조사 우선** |
| 보안 S2 | 투자사기 신고 증거 연결·사건 군집화 | 수사·감독·플랫폼 조사 담당자 | 중복 사건 병합, 담당 배정, 보전요청 자료 생성 | **2단계 조사 우선** |
| 보안 S3 | 수탁사 보안 증빙 진위·충족도 검토 | 금융회사 개인정보·보안 담당자 | 미충족 항목 반려, 보완과제 생성 | **조건부 유지** — 기존 관리 플랫폼과 차별 필요 |
| 기능 C1 | 계약서에서 현금흐름·채권보호 실행으로 | 중소기업 대표·재무 담당자 | 수금 일정 생성, 위험조항 표시, 팩토링 준비 | **2단계 조사 우선** |
| 기능 C2 | 규제 변경에서 영향업무·담당과제로 | 금융회사 준법·상품·운영 담당자 | 영향받는 문서·화면·프로세스에 수정과제 배정 | **조건부 유지** — 해외 시장은 이미 성숙 |
| 기능 C3 | 재난 신호에서 피해고객 선제지원 케이스로 | 금융회사·정책금융 운영 담당자 | 대상 후보 선별, 연락·증빙·지원 케이스 개설 | **탐색 유지** — 내부연계와 AI 필요성 검증 필요 |

현재 근거만 놓고 보면 S1, S2, C1은 `문제 → 판단 → 행동`의 연결이 가장 선명하다. S3와 C2는 문제는 분명하지만 기존 제품과 겹치는 범위가 넓다. C3는 연결 자체는 새롭지만 실제 기관 업무와 AI 역할에 대한 근거가 더 필요하다. 이 판단은 기존 후보인 정기결제·맞춤형 지원과의 비교 순위가 아니다.

## 1. 금융보안 후보

## S1. 무역송금 계좌변경 가드

### 한 문장

수출입기업이 송금 직전에 이메일·인보이스·과거 거래처 계좌·발신 도메인을 함께 비교하고, 계좌변경이나 사칭 징후가 있으면 **송금을 보류한 뒤 기존 연락처로 확인하는 업무를 자동 생성**하는 서비스다.

### 사용자와 현재 흐름

- 사용자: 해외 거래처에 대금을 보내는 중소 수출입기업 재무 담당자와 최종 결재자
- 현재: 메일로 받은 인보이스 확인 → 계좌번호 복사 → 내부 결재 또는 인터넷뱅킹 송금
- 핵심 문제: 공격자는 평소 인보이스 서식과 말투를 재사용하고, 실제 메일 계정을 탈취하거나 유사 도메인을 써서 계좌만 바꾼다. 메일 한 통만 보면 정상 거래처럼 보인다.
- 필요한 판단: `이번 계좌·발신자·요청 방식이 과거 거래관계와 일치하는가?`

### 서비스 흐름과 실제 행동

1. 사용자가 현재 이메일과 인보이스를 업로드한다.
2. 서비스가 과거 인보이스·거래처 마스터·정상 연락처와 비교한다.
3. 계좌 신규/변경, 유사 도메인, 급박한 송금 문구, 거래조건 불일치를 묶어 근거별로 표시한다.
4. 고위험이면 결재 상태를 `확인 필요`로 바꾸고 송금 보류 사유를 남긴다.
5. 공격자가 제공한 연락처가 아니라 기존에 등록된 연락처로 전화·영상통화 확인 업무를 배정한다.
6. 확인 결과와 담당자 서명을 저장한 뒤에만 결재 가능 상태로 전환한다.

은행 송금 API 없이도 MVP의 핵심 행동은 보여줄 수 있다. 실제 은행 이체를 막는 대신 서비스 안의 `결재 보류/해제` 상태와 검증 업무를 작동시키면 된다.

### 국내 문제 근거

- [한국무역보험공사 주의 안내](https://www.ksure.or.kr/rh-kr/bbs/i-412/detail.do?ntt_sn=575428)는 해커가 수출자·수입자 이메일을 해킹하고 수출자를 사칭해 결제계좌를 바꾸는 사고가 지속된다고 설명한다. 정상 인보이스 형식과 표현을 사용하며, 유사 이메일이나 해킹된 실제 이메일을 쓰기도 한다. 공사는 기존 연락처를 이용한 유선 확인과 계약서상 계좌변경 제한을 권고한다.
- [매일경제의 관세청 자료 보도](https://www.mk.co.kr/news/economy/11431486)에 따르면 2021년부터 2025년 상반기까지 무역사기 1,591건, 약 9,600만 달러 피해가 발생했고 이메일 해킹이 건수의 95.4%를 차지했다. 금융감독원도 송금 전 계좌 확인과 거래처 직접 연락을 권고했다.

이는 ‘보안 공부를 한번 하면 끝나는 문제’가 아니다. 거래마다 새 인보이스와 새 요청을 다시 판단해야 하고, 공격자가 정상 대화 맥락을 재사용하기 때문이다.

### 기존 서비스 층위와 빈틈

- **이미 있고 사용 가능한 층:** 국내외 이메일 보안·BEC 탐지 제품은 발신 도메인, 사칭, 악성 링크, 메일 내용 위험을 탐지한다. [ZeroAX의 BEC 설명](https://www.zeroax.com/blog/126640)도 계좌변경·긴급송금·수정 인보이스를 이용한 업무 프로세스 조작을 주요 형태로 설명한다.
- **해외에서 성숙한 층:** Trustpair, Eftsure, Trustmi, nsKnox 같은 제품군은 공급업체 계좌 검증과 지급 전 사기 방지를 제공한다. 따라서 아이디어 자체가 세계 최초는 아니다.
- **국내 통합 여부를 아직 모르는 층:** 공개된 국내 제품 설명만으로는 `메일·인보이스·과거 지급계좌·결재 보류·기존 연락처 확인`이 하나의 중소기업용 흐름으로 묶여 있는지 확인되지 않았다.
- **우리가 대체할 수 있는 비공식 우회:** 담당자가 과거 메일을 검색하고 거래처에 직접 전화하는 이중 확인. 효과는 있지만 담당자 습관에 의존하고 증적이 흩어진다.

따라서 차별점은 ‘피싱 메일 분류’가 아니라 **지급 직전 거래 맥락 비교와 보류 절차의 강제**여야 한다.

### 공개·합성 데이터 MVP

- 가상의 거래처 5곳, 과거 정상 인보이스 20개, 정상 연락처·계좌 마스터
- 정상 메일, 실제 메일 탈취형, 유사 도메인형, 계좌만 바뀐 인보이스형, 급박한 재송금형 시나리오
- 다국어 이메일/PDF에서 회사명·금액·통화·계좌·납기·연락처를 추출
- 최종 화면: 위험 근거, 과거값과 현재값 비교, `송금 보류`, `확인업무 배정`, `확인 완료 후 해제`

### AI가 필요한 지점

계좌번호 자체의 변경 비교는 규칙으로 충분하다. AI의 실질적 역할은 다국어 이메일과 다양한 인보이스에서 거래조건을 읽고, 정상 대화 맥락과 사칭 요청의 의미 차이를 찾는 것이다. 판정은 AI 단독이 아니라 규칙·이력·사람 확인을 결합해야 한다.

### 2단계에서 확인할 것

- 국내 ERP·그룹웨어·기업뱅킹에 유사한 지급보류 기능이 이미 있는지
- 거래처 계좌 소유자 검증 API 또는 은행의 수취인 확인 기능을 외부 서비스가 쓸 수 있는지
- 이메일·인보이스 업로드 시 영업비밀과 개인정보 처리 요건
- 중소 수출입기업 재무 담당자 3~5명의 실제 확인 절차와 사고 직전 징후

## S2. 투자사기 신고 증거 연결·사건 군집화

### 한 문장

리딩방·가상자산 투자사기 신고에 첨부된 채팅 캡처, 계좌번호, 전화번호, URL, 가짜 회사명과 신고 서술을 읽어 **같은 조직·캠페인으로 보이는 사건을 연결하고 담당자에게 병합·보전조치 후보를 제시**하는 조사 지원 서비스다.

### 사용자와 현재 흐름

- 사용자: 금융감독·경찰 수사 지원 인력, 플랫폼 신뢰·안전팀, 신고 접수·분류 담당자
- 현재: 피해자가 육하원칙의 서술과 관련 증거를 제출 → 담당자가 신고별로 읽고 관할·유형 분류 → 다른 신고의 계좌·별칭·URL과 수동 대조
- 핵심 문제: 같은 조직이 방 이름, 상담원 별칭, 사이트 도메인을 조금씩 바꾸며 여러 피해자를 만든다. 신고 한 건만 보면 단서 가치가 낮아도 여러 건을 연결하면 캠페인 구조가 보일 수 있다.

### 서비스 흐름과 실제 행동

1. 신고 서술, 채팅 캡처, 이체내역, URL을 입력한다.
2. OCR과 문서 분석으로 계좌·전화·도메인·메신저 ID·가짜 금융회사명·유도 문구를 추출한다.
3. 완전 일치뿐 아니라 유사 도메인, 반복 문구, 같은 입금 유도 단계 등 약한 연결도 그래프로 묶는다.
4. 기존 사건과의 연결 근거와 신뢰도를 보여준다.
5. 담당자가 `사건 병합`, `동일 캠페인 태그`, `담당부서 이관`, `계정·URL 보전요청 자료 생성` 중 하나를 승인한다.

지급정지·수사·사이트 차단을 서비스가 직접 집행한다고 주장하면 안 된다. 권한기관이 바로 검토할 수 있는 **사건 묶음과 공식 요청자료 초안**을 만드는 데까지가 현실적이다.

### 국내 문제 근거

- [금융감독원 가상자산 불공정거래·투자사기 신고센터](https://www.fss.or.kr/fss/main/contents.do?menuNo=201129)는 신고자가 육하원칙에 따라 상세히 적고 관련 증거자료를 제출하도록 한다. 일반 투자사기는 금감원이 직접 조사·조치할 권한이 없어 수사기관 신고가 필요할 수 있고, 신고는 소관부서로 이관되거나 수사기관에 통보될 수 있다. 동일 사항의 조사 진행 여부와 새 증거의 가치도 처리 판단에 들어간다.
- [경찰청 사이버범죄 예방의 계좌·전화번호 조회](https://cyberbureau.police.go.kr/prevention/sub7.jsp?mid=020600)와 [더치트 금융사기방지 API](https://kakaocloud.com/marketplace/services/thecheat)는 계좌·전화번호가 이미 피해사례에 등록됐는지 확인하는 유용한 기능을 제공한다.
- [전화금융사기 수사를 위한 웹스크래핑·공간 군집화 연구](https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART002629240)는 흩어진 데이터를 군집화해 수사에 활용하려는 실무 수요가 존재함을 보여준다.

### 기존 서비스 층위와 빈틈

- **이미 있고 사용성이 분명한 층:** 계좌·전화번호 단건 조회, 온라인 신고, 사건별 증거 첨부.
- **부분적으로 있는 층:** 수사기관 내부 사건관리·연관분석 시스템은 공개 정보가 적어 기능 수준을 판단하기 어렵다.
- **공개적으로 확인되지 않은 층:** 여러 기관·플랫폼의 멀티모달 신고자료를 계좌 외의 문구·이미지·유사 도메인까지 묶어 투자사기 캠페인으로 군집화하는 국내 공개 서비스.
- **비공식 우회:** 피해자 커뮤니티에서 같은 계좌·사이트·상담원 이름을 검색하거나 담당자가 엑셀로 대조한다. 유용하지만 오탐·명예훼손·개인정보 위험이 있고 공식 사건 근거로 바로 쓰기 어렵다.

핵심 차별은 ‘사기인지 알려주는 챗봇’이 아니라 **분리된 신고들을 하나의 조사 단위로 바꾸는 것**이다.

### 공개·합성 데이터 MVP

- 개인정보를 제거한 합성 신고 30~50건, 채팅 캡처·가짜 거래사이트·이체내역 이미지
- 4개 사기조직이 별칭·계좌·도메인을 일부 재사용하는 시나리오
- 결과: 사건 그래프, 연결 근거, 신규/기존 캠페인 분류, 담당자 검토 큐
- 행동: 병합 승인, 담당 배정, 증거 보전요청 목록 PDF/화면 생성

실제 신고 원문이 없어도 핵심인 `증거 추출 → 관계 연결 → 사건 상태 변경`은 합성 데이터로 시연할 수 있다.

### AI가 필요한 지점

채팅 이미지 OCR, 비정형 서술에서 개체 추출, 철자가 조금 다른 별칭·유사 도메인·반복 수법의 의미 연결에는 AI가 유효하다. 다만 사건 병합은 설명 가능한 근거와 사람 승인이 필수다.

### 2단계에서 확인할 것

- 실제 신고 접수 화면의 첨부파일 유형과 필드
- 경찰·금감원·거래소·메신저 플랫폼 간 이관 가능한 정보와 법적 근거
- 더치트 등 기존 데이터의 이용·재배포 가능 범위
- 내부 사건관리 시스템에 이미 있는 연관분석 기능
- 허위 연결로 인한 피해를 막는 임계치·이의제기·감사로그 설계

## S3. 수탁사 보안 증빙 진위·충족도 검토

### 한 문장

금융회사 수탁사가 체크리스트 답변과 함께 올린 정책서, 화면 캡처, 교육기록, 접근권한표를 읽어 **답변을 실제로 뒷받침하는지, 서로 모순되는지 확인하고 미충족 항목을 보완과제로 돌려보내는 서비스**다.

### 사용자와 현재 흐름

- 사용자: 금융회사 개인정보보호·정보보안 담당자, 수탁사 점검자, 금융보안 관련 점검기관
- 현재: 점검표 배포 → 수탁사 자가답변과 증빙 업로드 → 금융회사 또는 점검자가 서면 검토 → 미흡사항 보완 → 필요 시 현장점검
- 문제: ‘예’라고 체크했는지보다 첨부 증빙이 실제 항목을 충족하는지 읽는 데 시간이 든다. 같은 문서를 여러 항목에 재사용하거나, 정책서와 실제 화면·기간·담당자가 어긋날 수 있다.

### 서비스 흐름과 실제 행동

1. 점검기준과 수탁사의 답변·증빙 묶음을 업로드한다.
2. 각 항목에 필요한 주장, 기간, 책임자, 기술적 설정을 구조화한다.
3. 증빙에서 해당 근거가 실제로 있는지 문장·표·화면 단위로 인용한다.
4. 오래된 문서, 날짜·조직명 불일치, 답변과 증빙의 모순, 동일 증빙의 과도한 재사용을 표시한다.
5. 점검자는 `충족`, `보완요청`, `현장확인 필요` 중 하나를 승인한다.
6. 보완요청은 필요한 자료와 기한이 붙은 과제로 수탁사에 돌아간다.

### 국내 문제 근거

- [금융보안원의 개인(신용)정보 수탁자 합동점검](https://www.fsec.or.kr/bbs/1007)은 금융회사의 관리·감독 업무와 규제준수 비용을 줄이기 위해 수탁자 점검기준 개발, 서면·현장 점검, 결과 제공과 사후관리를 수행한다고 명시한다.
- [캐치시큐의 수탁사 점검 설명](https://www.catchsecu.com/archives/15645)은 원격점검에서 수탁사가 체크리스트에 따라 자체점검하고 증적자료를 제출하는 흐름을 설명한다.
- [KISCON의 수탁사 실태점검 서비스](https://kiscon.co.kr/services/subcontract.html)는 단순 점검표가 아니라 실제 이행을 증명하는 증빙 확보가 중요하다고 설명하며, 플랫폼에서 점검·증빙 관리·이행조치 확인을 지원한다.

### 기존 서비스 층위와 빈틈

- **차별이 필요한 층:** 우리가 만들 수 있는 부분은 또 하나의 점검관리 대시보드가 아니라, **첨부된 비정형 증빙의 내용이 답변을 실제로 입증하는지 인용과 함께 검토하는 심사 보조**다.
- **정보 부족:** 국내 기존 제품이 문서·화면 증빙의 의미적 충족도와 상호모순까지 어느 정도 자동 판정하는지는 공개 설명만으로 확인되지 않았다.

### 공개·합성 데이터 MVP

- 공개 점검 체크리스트와 가상의 수탁사 3곳
- 합성 내부관리계획, 교육 이수목록, 접근권한표, MFA 설정화면, 로그보관 정책
- 고의로 날짜 불일치, 퇴사자 권한 잔존, 정책과 화면 설정 불일치, 오래된 교육자료를 삽입
- 결과: 항목별 근거 인용, 충족/불충족/현장확인, 보완과제와 기한

### AI가 필요한 지점

문서·표·이미지에 흩어진 증거를 점검항목과 의미적으로 연결하고 서로 모순되는 주장을 찾는 데 AI가 필요하다. 보안설정의 실제 안전성 검증은 가능한 범위에서 규칙과 기술 스캐너로 보완해야 한다.

### 1단계 위험과 2단계 확인사항

- 기존 플랫폼이 이미 전 과정을 지원하므로, 증빙 내용 검증의 정확성과 시간절감이 명확하지 않으면 차별성이 없다.
- 실제 점검 증빙은 민감하여 공개 데이터가 거의 없을 수 있다. 합성 MVP는 가능하지만 실무 타당성 인터뷰가 중요하다.
- 2단계에서는 점검자 2~3명에게 ‘가장 오래 걸리는 증빙 5종’과 반복되는 부실증빙 유형을 물어야 한다.

## C1. 계약서에서 현금흐름·채권보호 실행으로

### 한 문장

중소기업이 공급계약서와 전자세금계산서를 올리면 지급기일·검수조건·지연 위험·채권양도 제한을 읽어 **수금 캘린더를 만들고 팩토링·매출채권보험에 필요한 보완사항과 신청 준비를 실행**하는 서비스다.

### 사용자와 현재 흐름

- 사용자: 별도 재무팀이 없거나 작은 중소기업 대표·경리·재무 담당자
- 현재: 계약서를 보관하고 세금계산서를 발행 → 지급일을 별도로 기록 → 자금이 부족하면 팩토링·보증·보험 제도를 검색 → 기관별 요건과 서류를 확인하고 신청
- 문제: 돈이 들어올 날짜와 금융 가능성은 계약서의 검수·정산·양도금지 조항, 세금계산서 발행 시점, 구매기업 동의 같은 문서 조건에 좌우된다. 그러나 회계·계약·금융지원 흐름이 분리돼 있다.

### 서비스 흐름과 실제 행동

1. 공급계약서와 세금계산서를 업로드한다.
2. 납품·검수·청구·지급 예정일, 지연이자, 상계, 채권양도금지, 구매기업 동의 조건을 추출한다.
3. 실제 입금 예상일과 자금 공백 구간을 달력으로 만든다.
4. 팩토링 또는 매출채권보험 가능성을 공개 요건으로 1차 점검한다.
5. `세금계산서 발행`, `구매기업 동의 요청`, `계약조항 확인`, `필요서류 발급`, `기관 신청페이지 이동`을 순서가 있는 작업으로 만든다.

법률 판단이나 금융 승인으로 표현하지 않고 `위험조항 후보`와 `신청 준비 가능성`으로 제한한다.

- 실행: 캘린더·체크리스트 생성, 구매기업 동의요청 초안, 기관별 준비 완료도와 공식 신청페이지 연결

### 2단계에서 확인할 것

- 중소기업 담당자가 계약서를 실제로 업로드할 의향과 보안 요구

## C2. 규제 변경에서 영향업무·담당과제로

### 한 문장

새 금융 규정·감독지침의 변경조항을 회사의 상품설명서·약관·상담스크립트·화면·내부통제 문서와 연결해 **무엇을 누가 언제 고쳐야 하는지 과제로 배정**하는 규제변경 실행 시스템이다.

### 사용자와 현재 흐름

- 사용자: 금융회사 준법감시, 법무, 상품, 채널 운영, 내부통제 담당자
- 현재: 새 공문·법령 수신 → 담당자가 신구조문과 해설을 읽음 → 관련 부서에 영향 여부 질의 → 상품·약관·스크립트·화면 수정 → 증적 취합
- 문제: 규제 정보의 발견보다 ‘우리 회사의 어느 산출물과 프로세스가 영향을 받는가’를 찾고 책임자를 정하는 단계가 어렵다.

### 서비스 흐름과 실제 행동

1. 개정 전후 규정과 시행일을 읽어 의무·금지·예외·기한을 추출한다.
2. 회사가 등록한 상품·프로세스·문서·화면 목록과 의미적으로 대조한다.
3. 영향을 받을 가능성이 높은 산출물과 근거 조항을 제시한다.
4. 조직표와 소유자 정보로 수정 담당자·검토자·기한을 제안한다.
5. 담당자는 과제를 승인하고, 변경된 산출물과 검토 서명을 연결해 종료한다.

AI가 ‘법적으로 위반’이라고 최종 판정하는 것이 아니라, 누락을 줄이는 영향분석 초안과 추적 가능한 업무흐름을 제공한다.

### 국내 문제 근거

- [Samsung SDS의 RegTech 적용 사례](https://www.samsungsds.com/kr/insights/regtech_2.html)는 법규·보험약관 같은 문서가 기계가 읽기 어려워 사람의 관여와 반복 수기작업이 발생하며, 금융기관 내 규제관리가 개별 시스템에 흩어져 전체 통제가 어렵다고 설명한다. 법규 변경 영향도 파악 가능성과 규제 관련 정보 통합 사례도 소개한다.
- 같은 자료는 규제가 복잡해지고 변경이 잦아 금융기관의 대응에 많은 시간과 비용이 든다고 지적한다.
- [국내 금융회사 내부통제·준법감시 IT 연구](https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART002733654)는 준법감시와 내부통제 업무의 IT 개선 필요성을 다룬다.

### 기존 서비스 층위와 빈틈

- **이미 있고 성숙한 해외 층:** Corlytics, Compliance.ai 등은 규제변경 수집, 의무 추출, 영향평가, 정책·통제 매핑을 제공한다. 해외에서는 ‘없는 기능’이라고 할 수 없다.
- **국내에서 이미 있는 층:** 금융보안원 레그테크 포털과 금융회사 자체 시스템은 규제정보, 보고, 점검, 현황 관리를 지원한다.
- **정보가 부족한 층:** 국내 중소 금융회사까지 쓸 수 있는 형태로 공개 공문에서 내부 상품 화면·스크립트·업무 소유자까지 연결하고 수정과제를 자동 생성하는 제품의 보급 수준.
- **비공식 우회:** 담당자가 신구조문표와 부서별 엑셀을 만들고 메일로 영향 여부를 회신받는다.

따라서 단순 규제 뉴스 요약이나 Q&A는 경쟁력이 없다. 특정 규제 1종과 내부 산출물 3종을 깊게 연결하는 좁은 MVP가 필요하다.

### 공개·합성 데이터 MVP

- 공개된 금융위·금감원 규정 개정 전후 문서
- 합성 금융상품 3개와 약관·상품설명서·상담스크립트·웹화면 텍스트
- 결과: 변경의무, 영향 후보, 근거 문장, 담당 부서와 마감일
- 실행: 수정과제 배정, 검토·승인 상태, 변경 전후 증적 묶음

### AI가 필요한 지점

법률문서의 신구 의미 변화와 다양한 내부 산출물 간의 관계를 찾는 데 AI가 필요하다. 시행일·금액·대상 같은 명시 규칙과 워크플로 상태는 결정론적으로 관리해야 한다.

### 1단계 위험과 2단계 확인사항

- 해외 제품이 이미 정확히 같은 문제를 다룬다. 국내 규제·한국어·조직업무 특화만으로 충분한 차별이 되는지 확인해야 한다.
- 회사 내부문서가 없으면 실전 정확도를 검증하기 어렵다.
- 2단계에서는 금융회사 준법 담당자의 실제 신구조문 영향분석 산출물과 기존 RegTech 도입 수준을 먼저 확인해야 한다.

## C3. 재난 신호에서 피해고객 선제지원 케이스로

### 한 문장

호우·산불 등 공개 재난구역과 금융회사의 가상 고객·대출 포트폴리오를 연결해 **피해 가능 고객을 먼저 찾고, 재해피해확인서·상환유예·긴급자금 안내와 담당자 연락 케이스를 개설**하는 기관용 운영 시스템이다.

### 사용자와 현재 흐름

- 사용자: 은행·카드·보험·정책금융기관의 재난지원 운영 담당자, 지자체 금융지원 협업 담당자
- 현재: 재난 발생 후 기관별 지원방안 공지 → 피해자가 지자체에 신고하고 재해피해확인서를 발급 → 금융회사에 직접 신청 → 기관이 심사해 만기연장·상환유예·보험금 등을 처리
- 문제: 지원제도는 생기지만 피해자가 제도를 발견하고 증빙을 받은 뒤 찾아와야 한다. 기관은 공개 재난정보와 자사 고객의 위치·상품을 연결해 선제적으로 누가 어떤 지원을 필요로 할지 보는 기능이 필요할 수 있다.

### 서비스 흐름과 실제 행동

1. 재난 경보·피해지역·기간과 기관별 지원공지를 수집한다.
2. 합성 고객의 사업장·담보 위치, 상품, 상환일정과 재난구역을 대조한다.
3. 피해 가능성, 가까운 납부·만기 일정, 이용 가능한 지원유형으로 우선순위를 정한다.
4. 담당자는 연락대상을 승인하고 `안내 발송`, `피해확인서 대기`, `상환유예 상담`, `현장확인` 케이스를 연다.
5. 증빙이 들어오면 상품별 필요서류와 처리부서로 넘긴다.

### 국내 문제 근거

- [금융위원회의 산불 피해 금융지원 안내](https://www.fsc.go.kr/edu/cardnews?cnId=2672&curPage=9&pastPage=9)는 긴급생활안정자금, 기존 대출 만기연장·상환유예 등 여러 지원을 안내한다.
- 금융위원회 자료들은 지원 신청을 위해 지자체가 발급하는 재해피해확인서를 먼저 준비하도록 안내한다. 즉 `재난 신고 → 확인서 → 금융회사 신청`이라는 기관 간 다단계 흐름이 존재한다.
- [정책브리핑의 집중호우 금융지원 안내](https://www.korea.kr/news/policyNewsView.do?newsId=148946732)는 은행·상호금융권의 긴급생활자금, 만기연장·상환유예 등 피해가정 지원을 안내한다.

### 기존 서비스 층위와 빈틈

- **이미 있는 층:** 재난안전포털의 피해신고, 금융위·은행별 지원공지, 금융감독원 1332 상담, 금융회사별 신청·심사.
- **인접 기능이 있는 층:** 금융회사는 연체·다중채무 등 위기차주를 내부 전산으로 선별하는 체계를 확대하고 있다. 기후리스크 분석 제품도 포트폴리오 위험을 계산한다.
- **공개적으로 확인되지 않은 층:** 재난구역과 실제 금융상품·다가오는 납부일을 연결해 피해자 신청 전에 지원 케이스를 여는 국내 공개 운영제품.
- **비공식 우회:** 전 지점 공지, 피해지역 고객의 자발적 신청 대기, 콜센터 문의 접수.

이 후보는 기존 ‘맞춤형 지원’과 다르다. 일반 사용자가 지원사업을 검색하는 서비스가 아니라 **재난 발생을 트리거로 기관이 자기 고객을 먼저 찾아 업무를 여는 시스템**이다.

### 공개·합성 데이터 MVP

- 공개 재난 경보·행정구역·지원공지
- 합성 고객 100명, 사업장 위치, 대출·카드·보험 상품과 납기
- 재난구역 안/밖, 고위험 업종, 곧 만기가 오는 고객을 섞은 시나리오
- 결과: 지도와 우선검토 큐, 고객별 가능한 지원과 필요한 확인서
- 실행: 연락 승인, 지원 케이스 개설, 증빙 대기·심사 이관 상태 전환

### AI가 필요한 지점

단순 지역 겹침과 일정 계산은 AI가 필요 없다. AI는 여러 기관의 비정형 지원공지에서 대상·조건·기한·필요서류를 구조화하고, 사진·서술형 피해신고를 담당자 검토용으로 정리하는 데 써야 한다. 이 역할이 약하면 공모전에서 ‘AI를 붙인 GIS/규칙 시스템’으로 보일 위험이 있다.

### 1단계 위험과 2단계 확인사항

- 실제 고객 위치·대출정보는 금융회사 내부 데이터이므로 합성 MVP 이후의 도입경로가 B2B에 한정된다.
- 위치만으로 피해자로 단정하거나 자동 불이익을 주면 안 된다. 선제 지원 연락 후보로만 사용해야 한다.
- 금융회사가 이미 재난지역 고객을 내부적으로 선별하는지 공개 정보가 부족하다.
- 2단계에서는 금융회사 재난지원 실무자 인터뷰, 고객 연락의 동의·법적 근거, 공개 재난 데이터의 해상도와 갱신속도를 확인해야 한다.

## 3. 조사했지만 이번 6개에서 뺀 아이디어

### 금융상품 광고 사전심의 AI

실무 문제는 분명하지만 2026년 은행연합회가 광고 초안·상품설명서·약관을 분석하고 법규·심의규정과 정합성을 확인하는 AI 광고심의 시스템을 추진한 사례가 확인됐다. 우리가 생각한 핵심 기능과 너무 가깝기 때문에 제외했다.

### 범용 금융 AI 에이전트 툴 호출 차단

[금융보안원의 AI 에이전트 보안 위협 보고](https://www.fsec.or.kr/bbs/detail?menuNo=69&bbsNo=11700)는 에이전트 하이재킹·도구 오염이 비정상 대출승인이나 공격자 계좌 이체로 이어질 수 있고, 사람 승인·최소권한·실시간 검증이 필요하다고 설명한다. 문제는 매우 적합하다.

그러나 [SmartM2M의 국내 생성형 AI 보안 솔루션](https://www.smartm2m.co.kr/sub110/)이 이미 프롬프트 인젝션 차단, 권한·화이트리스트 기반 Tool/MCP 호출 통제, 감사 로그를 공개 기능으로 제시한다. 공모전 예시에도 프론티어 AI 공격 방어가 포함되어 있어, 단순 가드레일은 신규성이 부족하다고 판단했다. 특정 금융거래의 사용자 의도·동의와 실제 툴 호출을 대조하는 좁은 문제로 재정의할 때만 재검토할 수 있다.

### 민원 분석·상품개선 AI

금융회사와 감독당국이 이미 민원·분쟁사례를 AI로 분석하고 위험상품·불완전판매를 찾는 사업을 확대하고 있다. ‘민원 요약 대시보드’ 수준으로는 실제 행동과 신규성이 약해 제외했다.

### 거래처 신용위험 알림

신용조회·변동 모니터링·매출채권보험이 이미 존재하고, 비상장 중소기업을 공개·무료 데이터만으로 신뢰성 있게 평가하기 어렵다. 기존 서비스를 넘는 연결이 약해 제외했다.

## 4. 팀 논의를 위한 선택 기준

이번 단계에서는 성공점수나 최종 순위를 고정하지 않는다. 대신 각 후보에 대해 아래 네 질문만 보면 된다.

1. **장면이 보이는가:** 사용자가 어떤 문서·사건을 보고 어떤 버튼을 누르는지 설명할 수 있는가?
2. **상태가 바뀌는가:** 조회·요약을 넘어 보류, 병합, 반려, 과제배정, 신청준비, 케이스개설이 일어나는가?
3. **합성 데이터로도 핵심을 증명할 수 있는가:** 실제 은행 API나 내부 원장을 못 받아도 판단과 행동의 중심을 시연할 수 있는가?
4. **기존 제품과 다른 한 문장이 있는가:** ‘AI로 편하게’가 아니라 기존 제품이 끊기는 지점을 정확히 말할 수 있는가?

팀에서 2개 정도를 고르면 다음 단계에서는 사용자 인터뷰 질문, 기존 서비스 직접 비교표, 인증·API·법적 권한, MVP 화면과 테스트 시나리오까지 깊게 파면 된다.

## 5. 출처 사용 주의

- ‘통합 서비스가 없다’고 단정하지 않았다. 공개 제품 설명에서 확인되지 않은 경우는 모두 추가조사 대상으로 표시했다.
- 뉴스와 기업 블로그는 문제·제품 존재를 찾는 단서로 사용했고, 가능한 경우 금융위원회·금융감독원·금융보안원·공공기관 자료로 교차확인했다.
- 실제 신고·거래·고객 데이터는 개인정보와 영업비밀 문제가 있으므로 1단계 MVP는 공개 문서와 합성 데이터가 기본이다.
